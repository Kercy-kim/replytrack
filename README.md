# ReplyTrack

> 고객센터 대화에서 빠진 답변과 아직 이행되지 않은 약속을 확인하는 개인용 AI 상담 관리 서비스

프로젝트 기획과 로컬 시제품의 사용 방법을 정리한 README입니다. 핵심 흐름을 실행할 수 있는 웹 MVP와 선택한 대화를 분석하는 Chrome 확장 프로그램을 제공합니다.

## 1. 프로젝트 개요

ReplyTrack은 사용자가 고객센터와 나눈 대화를 입력하면, 생성형 AI가 질문과 요청을 항목별로 정리하고 답변의 충족 여부 및 처리 약속을 추적하는 서비스입니다.

제품 수리나 교환을 문의할 때는 비용, 처리 기간, 배송 방법 등 여러 가지를 한꺼번에 묻게 됩니다. 그러나 일부 내용만 답변받거나 “확인 후 안내하겠습니다”라는 답변을 받은 채 상담이 끝나기도 합니다. 사용자는 이전 대화를 다시 읽어 무엇이 해결됐는지 확인해야 하고, 상담 채널이나 담당자가 바뀌면 같은 상황을 반복해서 설명해야 합니다.

예를 들어 “수리비는 얼마인가요? 입고 후 수리는 며칠 걸리나요? 왕복 배송비는 누가 부담하나요?”라고 문의했는데 수리 기간만 안내받았다면, AI가 남은 질문을 찾아 보여 줍니다. 수리비를 점검 후 안내하겠다는 약속이 있는 경우에는 단순 미답변과 구분하여 답변 대기로 표시합니다.

또한 답변을 받은 상태와 실제 처리가 끝난 상태를 구분합니다. “환불해 드리겠습니다”는 처리 약속으로 기록하고, 사용자가 실제 처리 결과를 확인하면 완료 상태로 변경합니다. 새 답변을 추가하면 기존 질문에 연결하고, 아직 필요한 내용만 포함한 재문의 초안을 작성합니다.

초기에는 온라인에서 구매한 제품의 A/S 상담을 대상으로 개발합니다. 사용자가 직접 입력한 텍스트와 대화 캡처를 바탕으로 질문별 확인표, 원문 근거, 처리 상태를 관리하는 웹 시제품을 만드는 것이 목표입니다.

### 실행하기

**Node.js 24 이상**에서 실행합니다. 외부 패키지 설치나 빌드 과정은 없습니다.

```powershell
node server.mjs
```

브라우저에서 [http://127.0.0.1:3100](http://127.0.0.1:3100)을 엽니다.

- **빠른 시연:** `예제 상담 열기` → 질문별 상태 확인 → `재문의 · 인계` → 초안 생성 → `예제 답변 추가하기` → `견적 도착 시연하기` → 실제 결과 직접 확인. 예제는 준비된 가상 데이터로 동작하며 AI API를 호출하지 않는다고 화면에 표시합니다.
- **실제 AI 분석:** `AI 연결 설정`에서 OpenAI API 키를 등록합니다. 키는 서버 메모리에만 유지됩니다. `새 상담 시작하기`에서 텍스트 또는 캡처를 입력하고, AI가 읽은 발화자·원문·날짜를 검토한 뒤 분석합니다. 직접 메시지를 나누어 입력할 수도 있습니다.
- **환경변수 사용:** `.env.example`을 참고해 로컬 `.env`에 `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정할 수 있습니다. 기본 모델은 `gpt-5-mini`입니다. `.env`와 상담 데이터는 Git에서 제외합니다. API 키를 README나 소스 코드에 넣지 않습니다.
- **저장:** 상담 원문과 분석 결과는 `data/replytrack.sqlite`에 저장됩니다. 재시작해도 기록이 유지되며, `내려받기`로 Markdown을 내려받을 수 있습니다. 초안을 직접 고친 뒤 `편집 저장`을 누르면 새로고침 후에도 유지됩니다. 원본 캡처는 저장하지 않습니다.

현재 구현에는 텍스트·캡처 읽기, 질문별 근거와 상태, 사용자 수정, 약속·기한과 실제 확인 분리, 추가 답변 반영, 재문의·인계 초안, 변경 이력, 모바일 화면이 포함됩니다. 웹 홈에서 제목·업체 검색, 남은 질문·기한·미분석·보관 필터와 우선순위 정렬을 사용할 수 있습니다. 상세 화면의 `상담 관리`에서 제목·업체를 수정하거나 상담을 보관·복원합니다. 보관은 실제 문제 해결을 뜻하지 않습니다. 로컬 단일 사용자용이며 계정·자동 발송·알림·통화 녹취 기능은 포함하지 않습니다.

실행·검증 방법은 [개발 안내](docs/DEVELOPMENT.md), 발표 순서는 [시연 안내](docs/DEMO.md), 검증 범위와 결과는 [검증 기록](docs/VALIDATION.md)에 정리했습니다. 초기 MVP는 [Issue #1](https://github.com/Kercy-kim/tripsketch-ai/issues/1), 웹 사용성 개선은 [Issue #2](https://github.com/Kercy-kim/tripsketch-ai/issues/2)에서 추적합니다.

배송·환불·구독 가상 상담 20건의 실제 API 평가와 수정 전후 결과는 [AI 품질 평가 보고서](docs/AI-EVALUATION.md)에 있습니다. 입력·정답·원본 응답·중간 실패 결과와 재실행 도구도 함께 보관합니다.

이전 [상태 기준 재평가](docs/STATUS-BOUNDARY-EVALUATION.md)에서는 남았던 두 사례의 기준을 명확히 하고, 기존 20건과 추가 경계 8건의 분석 기준을 모두 통과했습니다.

이전 [새 상담 20건 평가](docs/UNSEEN-EVALUATION.md)는 기존 원문을 재사용하지 않은 배송 7·환불 7·구독 6건으로 진행했습니다. 최초 분석은 **17/20건**, 수정 후 같은 자료의 회귀 평가는 **20/20건**(질문 상태 32/32회, 약속·기한 8/8회)이었습니다. 초안 6건도 생성·검토 후 원문과 대조했습니다. 실패한 중간 실행과 기존 사례의 회귀 문제도 보고서에 보존하며, 일반 정확도 100%나 외부 사람의 검수를 뜻하지 않습니다.

이전 단계에서 같은 모델·상담 20건으로 비교한 [AI 성능 최적화](docs/AI-PERFORMANCE.md)에서는 총 토큰이 **7.2% 감소**했고, 분석 완료 중앙값은 **23.0초→16.2초**, 재문의는 **15.1초→10.6초**로 줄었습니다. 분석 20/20건·초안 6/6건을 통과했으며 원문·검토·수정 한도를 유지했습니다. 인계 중앙값은 30.9초→58.1초로 증가한 한계가 있고, 캐시·공급자 변동을 통제한 실험은 아닙니다. 중간 실패와 최종 회귀 결과도 함께 보관합니다.

후속 [인계 응답 시간 개선](docs/HANDOFF-PERFORMANCE.md)에서는 같은 분석 기록 12개로 전후 각각 18회 비교해 **중앙값 38.02초→17.35초(54.4% 감소)**, **p95 96.81초→51.88초**를 확인했습니다. 개선안 18회는 모두 저장·원문 대조를 통과했고, 검토 대조 16개와 자동 테스트 82개도 통과했습니다. 기준 구현 1회의 미완성 실패 시간도 포함했습니다. 해당 호출의 토큰 사용량은 알 수 없어 전체 절감률은 계산하지 않았으며, 양쪽 성공·사용량 확인 가능한 17쌍에서는 총 토큰이 28.1% 줄었습니다. 이전 인계 3건 평가와는 다른 표본이고, 수정이 필요한 경우의 긴 대기와 공급자 변동은 남아 있습니다.

이후 [50초 초과 인계 개선](docs/HANDOFF-TAIL-PERFORMANCE.md)에서는 같은 기록 12개 중 느린 사례를 반복해 전후 각 20회를 비교했습니다. **50초 초과 1→0회, 최장 54.92→45.58초, 중앙값 18.04→15.60초, p95 22.64→21.68초**, 총 토큰은 5.31% 감소했습니다. 개선안의 전체 인계 20회와 별도 실패 초안 수정 8회는 모두 저장·원문 대조를 통과했고 자동 테스트 86개도 통과했습니다. 모호한 생성 예시를 고치고 내부 ID 표기만 코드로 정리하며, 의미 수정·검토는 medium을 유지합니다. 수정 경로만의 측정에는 기준의 빠른 실패 2회가 포함되어 중앙값·총 토큰이 오히려 늘었고, 전체 생성의 일부 쌍도 느려졌습니다. 반복한 합성 자료의 결과이며 모든 요청의 50초 이내 완료를 보장하지 않습니다.

추가 [45초 초과 인계 개선](docs/HANDOFF-ATTRIBUTION-PERFORMANCE.md)은 근거 없는 담당자 구분을 제한된 안내 전달 표현에서 정리해 재생성 호출을 줄입니다. 원래 45.58초 사례의 같은 실패 초안을 재생했을 때 수정·검토 구간은 **20.46~28.74초→8.34~9.07초**였으며 기존 medium AI 검토를 통과했습니다. 전체 생성 전후 20회에서는 최장 **46.49→34.59초**, 45초 초과 **1→0회**였지만 p95는 **33.00→33.26초**로 소폭 증가했습니다. 이 전체 실행에는 새 정리 경로가 적용되지 않아 시간 차이를 코드 효과로 단정하지 않으며, 적용 경로는 별도 고정 초안 재생으로 검증합니다. 생성·수정·검토 지침과 추론량은 유지하고 자동 테스트 94개를 통과했습니다. 정정 순서 등 다른 오류에 따른 재작업은 남아 있습니다.

### Chrome 확장 프로그램

웹을 유지하면서 고객센터 대화를 Chrome 옆 패널에서 분석할 수 있습니다. `node server.mjs`로 서버를 켜고 웹에서 AI 연결을 설정한 뒤, `chrome://extensions`의 개발자 모드에서 이 저장소의 **`extension` 폴더**를 로드합니다.

**대화 드래그 → ReplyTrack 아이콘 또는 우클릭 가져오기 → 원문·발화자 확인 → 질문별 상태와 근거 → 재문의 초안 편집·복사** 순서로 사용합니다. 분석한 상담은 같은 로컬 DB에 저장되며 **웹에서 기록·수정**으로 이어집니다. 새 답변 추가와 실제 처리 확인은 기존 웹에서 진행합니다.

확장은 사용자가 선택한 텍스트만 가져오며 자동 발송하지 않습니다. 분석에는 실행 중인 로컬 서버와 실제 AI 연결이 필요합니다. 설치, 지원 범위, 권한, 시연과 검증은 [Chrome 확장 안내](docs/EXTENSION.md)를 참고합니다.

## 2. 개발 목적

- 긴 상담 내용을 다시 읽으며 미해결 질문을 찾는 수고를 줄입니다.
- 질문별로 답변받은 내용과 추가로 확인해야 할 내용을 구분합니다.
- 업체가 안내한 처리 약속과 실제 완료 여부를 따로 확인할 수 있게 합니다.
- 상담 채널이나 담당자가 바뀌어도 이전 상황을 이어서 설명할 수 있도록 돕습니다.
- 원문 근거를 확인하고 수정할 수 있는 AI 분석 결과와 재문의 초안을 제공합니다.

### 기존 서비스와의 차별점

| 비교 서비스 | 공개적으로 확인되는 기능 | ReplyTrack의 개선 방향 |
| --- | --- | --- |
| [Resolver](https://www.resolver.co.uk/about) | 소비자 문의별 기록 생성, 증거 첨부, 대화와 진행 상황 관리 | 상담 기록 속 질문을 개별 항목으로 나누고 각 질문의 답변 충족 여부를 원문과 대조합니다. |
| [NoReply](https://usenoreply.com/changelog/ai-chat-on-cases) | 사건의 증거와 진행 상황을 이해하는 AI 대화, 다음 대응 안내 및 문의글 작성 | 질문·답변·처리 약속을 구분하고, 미답변·답변 대기·처리 확인 필요 항목을 계속 갱신합니다. |
| [Intercom](https://www.intercom.com/help/en/articles/7837533-fin-ai-agent-reporting) | 기업의 상담 운영을 위한 AI 대화 해결 상태와 성과 분석 | 소비자가 직접 가져온 여러 채널의 상담 자료를 자신의 요청 항목 기준으로 관리합니다. |

핵심 차별화 목표는 **질문별 답변 충족 여부를 원문 근거와 함께 보여 주고, 답변 수신과 실제 처리 완료를 구분하며, 새 답변이 올 때마다 남은 문제를 갱신하는 것**입니다. 대화 요약과 문의글 작성에 이 세 기능을 결합하여 상담 과정에서 놓치는 내용을 줄이고자 합니다.

위 비교는 공개된 기능 설명을 기준으로 정리한 개선 방향입니다. 경쟁 서비스의 모든 기능을 직접 검증한 결과나 해당 기능이 시장에 전혀 없다는 주장은 아닙니다.

## 3. 예상 사용자

| 사용자 | 필요한 도움 |
| --- | --- |
| 온라인 구매 제품의 수리·교환을 문의하는 소비자 | 비용, 기간, 배송 조건 중 답변받지 못한 내용 확인 |
| 여러 차례 고객센터에 문의한 사람 | 이전 설명과 새 답변을 연결하고 미해결 항목 추적 |
| 이메일·문자·채팅 등 여러 채널로 상담하는 사람 | 흩어진 상담 자료와 처리 약속을 한곳에서 확인 |
| 긴 대화를 다시 읽을 시간이 부족한 사람 | 근거가 연결된 확인표와 간단한 재문의 초안 작성 |

| 상담 자료 등록과 질문 정리 | 상담 텍스트, 대화 캡처, 상담 제목 | AI가 발화자와 질문·요청을 추출하고, 사용자가 인식 결과를 확인·수정합니다. | 원문과 연결된 질문 카드 |
| 질문별 답변 검증 | 질문 카드와 고객센터 답변 | AI가 질문의 의도, 답변의 범위, 조건과 대기 약속을 비교합니다. | 답변 상태, 판단 이유, 근거 문장 |
| 약속·기한·처리 상태 추적 | 처리 약속이 담긴 답변과 사용자 확인 | AI가 약속한 행동·기한을 추출하고, 서버가 날짜와 상태를 관리합니다. | 처리 약속 목록, 기한, 업체 안내와 사용자 확인 상태 |
| 미해결 항목 재문의 초안 | 남은 질문과 확인된 상담 사실 | AI가 아직 필요한 내용만 포함하여 간결한 재문의 문장을 생성합니다. | 수정·저장·복사할 수 있는 초안과 편집 전 생성 결과 |
| 추가 답변 반영과 상담 인계 요약 | 기존 상담 기록과 새 답변 | AI가 새 답변을 기존 질문에 연결하고, 변경 내용과 남은 요청을 정리합니다. | 갱신된 확인표, 변경 이력, 다른 상담원에게 전달할 요약 |
| 새 답변 반영 전후 비교 | 검증을 마친 분석 전후의 질문·약속 | 서버가 실제 상태와 기한·약속 내용의 차이를 비교합니다. 비교를 위한 추가 AI 호출은 없습니다. | 이번에 바뀐 질문 상태·AI 제안·약속, 이전 → 이번 분석, 근거 원문, 과거 비교 기록 |
| 상담 목록과 기록 관리 | 제목·업체 검색, 필터, 보관 선택 | 추출된 질문·약속과 한국 시간의 날짜로 우선순위를 계산합니다. 이 기능 자체는 추가 AI 호출 없이 동작합니다. | 검색 결과, 기한 안내, 수정한 상담 정보, 보관함과 복원 |

답변 상태는 **미답변·부분 답변·답변 대기·답변 받음·확인 필요**로 구분합니다. 사용자는 원문 근거와 판정 이유를 확인하고 직접 수정할 수 있습니다.

| 상태 | 구분 기준 | 예시 |
| --- | --- | --- |
| 미답변 | 해당 질문에 관련된 안내 자체가 없음. 인사만 하거나 다른 문제를 안내한 경우 포함 | 배송 위치를 물었는데 인사만 받음 |
| 부분 답변 | 같은 문제의 방법·조건·일부 정보는 있지만 요청한 개별 결과나 전체 범위는 빠져 있음 | 실제 해지 여부를 물었는데 해지 방법만 안내받음 |
| 확인 필요 | 관련 응답은 있지만 실질 정보 없이 미정이라고 하거나, 모호함·충돌·근거 검증 실패로 직접 확인이 필요함 | 환불액을 물었는데 아직 안내할 정보가 없다는 답을 받음 |

남은 정보를 나중에 안내하겠다는 명시적 약속이 있으면 **답변 대기**, 요구한 정보가 모두 제공되면 **답변 받음**입니다. 최신 정정과 충돌, 부분 정보와 향후 안내 약속이 함께 있을 때의 우선순위는 [상태 판정 기준](docs/adr/0006-question-status-boundaries.md)에 정리했습니다. 정보 미정이나 방법 안내도 해당 업체 답변을 근거로 남깁니다.

처리 상태는 답변 상태와 별도로 **처리 약속·업체의 처리 안내·사용자 확인 완료**를 관리합니다. 기한이 명시되지 않았거나 기준 날짜가 불분명하면 기한 미정으로 남깁니다. 한국 시간 기준으로 오늘까지·기한 지남을 표시하되, 기한 경과를 처리 실패로 단정하지 않습니다. 업체의 답변만으로 실제 처리 완료를 확정하지 않습니다.

초기 시제품의 입력 방식은 텍스트 붙여넣기와 대화 캡처 업로드입니다. 재문의는 초안을 확인하고 복사하는 방식으로 제공하며, 법적 책임이나 보상 가능성을 판정하는 기능은 초기 범위에 포함하지 않습니다.

## 5. 간단한 사용 예시

1. 사용자가 수리비, 입고 후 수리 기간, 왕복 배송비 부담 주체를 물어본 상담 내용을 등록합니다.
2. AI가 세 가지 질문을 분리하고, 사용자가 추출된 내용을 확인합니다.
3. 고객센터의 “입고 후 수리는 3~5영업일 정도 소요되며, 수리비는 점검 후 안내하겠습니다”라는 답변을 분석합니다.
4. 수리 기간은 답변 받음, 수리비는 답변 대기, 왕복 배송비는 미답변으로 표시합니다.
5. 사용자가 각 상태의 근거를 확인하고, 견적 안내 예정일과 배송비 부담 주체를 묻는 재문의 초안을 복사합니다.
6. 새 답변으로 “왕복 배송비는 업체에서 부담하며, 내일까지 견적을 안내하겠습니다”를 추가하면 **이번 답변으로 달라진 점**에서 배송비의 `미답변 → 답변 받음`, 견적 기한의 `기한 미정 → 날짜 확정`을 함께 확인합니다. 날짜 계산에는 실제 상담 시각이 필요합니다.
7. 실제 견적을 받은 뒤 사용자가 확인하면 해당 안내 약속을 사용자 확인 완료로 변경합니다.

위 예시는 기능 설명을 위한 가상 상황입니다.

비교는 분석에 성공한 시점의 기록입니다. 첫 분석은 비교 대상으로 표시하지 않으며, 같은 원문을 다시 분석한 결과와 새 답변 반영을 구분합니다. 변화가 없으면 그대로 안내하고, 분석 실패 시 마지막 성공한 비교를 이전 기록으로 표시합니다. 직접 지정한 질문 상태는 유지하고 바뀐 AI 제안을 따로 보여 줍니다. 약속의 업체 처리 안내는 사용자 확인 완료와 구분합니다. `변경 이력`의 **반영 전후 비교 보기**에서 이전 분석의 차이도 다시 볼 수 있습니다.

## 6. 시스템 구조

현재 시제품은 HTML·CSS·JavaScript 화면, Node.js HTTP 서버, OpenAI Responses API, SQLite 데이터베이스로 구성합니다. 설치 과정과 실행 환경을 단순하게 만들기 위해 Node.js 내장 기능을 사용합니다.

| 구성 요소 | 역할 |
| --- | --- |
| 사용자 화면 | 상담 자료 입력, 질문별 상태·원문 확인, 추가 답변 등록, 초안 수정·복사 |
| 서버 | 상담별 데이터 관리, 근거 참조 확인, 기한 계산, 사용자 확인과 변경 이력 저장 |
| 상담 자료 처리 | 텍스트·이미지에서 대화 내용을 읽고 메시지별 원문 참조 부여 |
| 생성형 AI | 질문·약속 추출, 답변의 의미 비교, 기존 질문 연결, 재문의와 인계 요약 작성 |
| 데이터베이스 | 원문, 질문, 답변 근거, 처리 약속, 상태, 사용자 수정 내용 저장 |

기본 처리 흐름은 **자료 입력 → 질문·약속 추출 → 사용자 확인 → 답변 대조 → 근거와 상태 표시 → 재문의 초안 생성**입니다. 새 답변은 같은 상담 기록에 추가하고 기존 질문을 갱신합니다.

서버는 AI가 인용한 메시지·발화자·근거 문장이 입력 자료에 실제로 존재하는지 확인합니다. 분석에 실패하면 기존 기록을 유지하고 재시도할 수 있습니다. 추가 답변은 분석 전에 먼저 저장하고, 버전 검사를 통해 오래된 분석이 최신 사용자 수정을 덮어쓰지 않도록 합니다. 설계 결정은 [ADR 0001](docs/adr/0001-local-mvp.md)에 기록했습니다.

## 7. UI/UX 구상

사용자가 원문과 AI 분석 결과를 함께 확인하고, 남은 질문을 쉽게 찾을 수 있도록 구성합니다.

| 화면 | 주요 내용 |
| --- | --- |
| 상담 목록 화면 | 상담 제목, 업체명, 미해결 항목 수, 마지막 업데이트 |
| 자료 입력 화면 | 텍스트·캡처 등록, 발화자·날짜·추출된 질문 확인 및 수정 |
| 상담 상세 화면 | 원문 대화, 질문별 확인표, 근거 문장, 처리 약속과 기한, 새 답변 추가 |
| 재문의·인계 화면 | 남은 질문 선택, 재문의 초안과 상황 요약, 수정·복사 버튼 |

**간단한 화면 예시**

- 입력 화면: “고객센터와 나눈 대화를 붙여넣어 주세요” 입력창과 “질문 정리하기” 버튼
- 상세 화면: “수리비: 답변 대기 / 수리 기간: 답변 받음 / 배송비: 미답변” 카드
- 근거 확인: 카드를 누르면 관련 원문이 강조되고 판정 이유와 수정 버튼 표시
- 약속 확인: “견적 안내: 내일 예정 / 사용자 확인 전”과 실제 수신 확인 버튼
- 재문의 화면: 남은 질문만 포함한 문장과 “초안 복사” 버튼

모바일에서는 원문과 분석 결과를 탭으로 전환하고, 넓은 화면에서는 나란히 배치합니다. 상태는 색상과 글자를 함께 사용하여 구분하며, 사용자가 수정한 내용은 변경 이력에 남깁니다.

## 8. AI 활용방안

AI는 형식이 일정하지 않은 상담 문장과 캡처를 이해하고, 질문과 답변의 의미를 비교하는 데 활용합니다.

- **질문·요청 추출:** 한 문장에 섞인 비용, 기간, 방법 등의 질문을 개별 항목으로 정리합니다.
- **답변 충족 여부 분석:** “배송비는 확인 중입니다”, “고객님 부담입니다”, “제품 불량이면 면제됩니다”의 차이를 해석하고 질문에 필요한 범위가 설명됐는지 판단합니다.
- **약속과 조건 해석:** 처리할 행동, 안내 시점, 선행 조건을 추출합니다. “점검 후 안내”처럼 기한이 불명확한 내용은 확인 대상으로 남깁니다.
- **추가 답변 연결:** 새 답변이 어떤 기존 질문에 해당하는지 찾고, 조건 변화나 상충하는 설명을 함께 제시합니다.
- **문장 생성:** 확인된 사실과 미해결 항목을 바탕으로 재문의 초안, 판정 이유, 상담 인계용 요약을 작성합니다.

단순히 특정 단어가 등장했는지 확인하는 방식으로는 조건부 답변과 처리 약속을 구분하기 어렵기 때문에 생성형 AI의 문맥 이해를 활용합니다. 날짜 계산, 데이터 저장, 근거 참조 확인, 상태 변경 이력 관리는 서버가 담당합니다.

AI의 답변 충족 판정은 업체 설명의 사실 여부나 법적 타당성을 보증하지 않습니다. 근거가 부족하면 확인 필요로 남기고 사용자가 수정할 수 있습니다. 현재는 `gpt-5-mini`와 JSON 스키마를 사용하는 Structured Outputs로 분석 구조를 고정하고, 서버에서 근거 참조와 초안의 숫자·기한을 추가 검증합니다. 이 검증만으로 모든 의미적 오류나 환각을 방지할 수 있는 것은 아닙니다. 여러 모델의 한국어 품질·비용·응답 시간 비교는 후속 평가로 진행합니다.

실제 초안은 생성 뒤 선택 질문의 누락, 소비자 관점, 원문 사실과 안내 순서를 별도로 AI 검토하고 필요하면 한 번만 수정합니다. 분석·의미 검토·초안 수정은 reasoning effort `medium`, 재문의와 인계의 첫 생성은 `low`를 사용합니다. 인계에는 별도 생성 지침과 질문 범위·미해결 상충을 확인하는 추가 검토 기준을 적용합니다. 초안 한 건에 보통 2회, 수정 시 최대 4회의 API 호출이 발생합니다. 서버는 원문에 없는 담당자 구분 표현도 차단하며, 검토 실패 시 기존 초안을 보존합니다. 분석의 원문 ID는 실제 대화와 발화자별 목록으로 제한하고, 인용문의 실제 존재도 검증합니다. 인용이 틀린 분석은 한 번만 수정 요청하며 재검증에 실패하면 이전 기록을 보존합니다. 근거가 있는 확인 필요 질문은 부분 정보 유무를 한 번 더 검토하며 답변 받음으로 승격하지 않습니다(분석당 최대 3회 호출, 합산 사용량 기록). 초안 생성·검토에는 AI의 추천 질문이나 추정 설명을 원문 사실처럼 전달하지 않습니다. 기한을 새 날짜로 변경한 경우에는 새 날짜를 반영하고, 대체 기한 없이 명시적으로 철회한 경우에만 현재 기한에서 제거합니다. 변경 이력은 보존하며 답변 대기는 연결된 향후 안내 약속의 근거도 확인합니다.

## 9. 개발 일정

기획, 설계, 기능 구현, 검증, 발표 준비를 포함한 총 5주의 개발 계획으로 구성합니다. 아래 일정은 계획 단계의 주차별 목표이며 완료 이력을 의미하지 않습니다.

| 기간 | 주요 작업 | 결과물 |
| --- | --- | --- |
| 1주차 | 문제 정의, 기존 서비스 조사, 요구사항·핵심 기능 확정, 화면·데이터 설계, 가상 상담 자료 준비 | 프로젝트 기획서, 기능 명세, 화면 구성안, 초기 예제 자료 |
| 2주차 | 상담 텍스트·캡처 입력, 인식 결과 확인, 질문 추출, 상담 기록 저장 구현 | 자료 입력과 질문 카드 생성이 가능한 기본 시제품 |
| 3주차 | 질문별 답변 검증, 원문 근거 연결, 처리 약속·기한 추출, 답변 상태와 처리 상태 분리 | 근거와 상태를 확인할 수 있는 상담 상세 화면 |
| 4주차 | 추가 답변 반영, 미해결 항목 재문의 초안, 상담 인계 요약, 사용자 수정과 변경 이력 연결 | 전체 사용 흐름이 연결된 통합 시제품 |
| 5주차 | 기능·AI 품질·사용성 평가, 오류 수정, README·보고서 정리, 30초 시연 영상과 발표 자료 제작 | 평가 결과, 최종 시연 버전, 최종 제출 자료 |

1주차 말에 개발 범위와 화면 구성을 확정하고, 3주차 말에는 핵심 분석 기능을 점검합니다. 4주차 말까지 전체 흐름을 연결하며, 5주차에는 평가와 오류 수정 및 발표 준비에 집중합니다.

## 10. 기대 효과 및 향후 계획

사용자는 긴 상담을 다시 읽는 시간을 줄이고, 이미 안내받은 내용과 남은 질문을 한눈에 확인할 수 있을 것으로 기대합니다. 처리 약속과 실제 결과를 구분하여 확인 누락을 줄이고, 담당자가 바뀌었을 때 이전 상황을 이어서 설명하는 데 도움을 줄 수 있습니다.

2026년 11월 14일 기존 20건과 경계 8건에 이어, 원문이 겹치지 않는 새 가상 상담 20건을 실제 API로 평가했습니다. 새 자료의 최초 분석 통과는 17/20건이며, 단순 안내의 약속 오인·완료 통보 누락·변경 기한 오류를 수정한 뒤 동일 자료의 분석은 20/20건을 통과했습니다. 질문 상태 32/32회, 기대 약속·기한 8/8회, 미해결을 답변 받음으로 표시한 오류 0/15회였고 초안 6건은 별도로 원문과 대조했습니다. 근거 검증·경계 검토·초안 입력 분리도 보완했습니다.

[새 상담 평가 보고서](docs/UNSEEN-EVALUATION.md)에 최초 결과와 수정 후 회귀, 기존 자료에서 다시 발견한 오류, 최종 코드의 검사 범위, 시간·사용량 증가를 구분해 기록했습니다. 과거 28건의 이전 통과 기록은 [상태 기준 재평가 보고서](docs/STATUS-BOUNDARY-EVALUATION.md)에 있으며, 최신 코드로 28건 전체를 다시 통과했다는 뜻은 아닙니다. 정답 작성과 원문 대조는 개발 에이전트가 수행했고 실제 사용자 전체의 정확도나 비용 절감을 입증하지 않았습니다. 외부 사람 검수와 남은 질문을 찾는 시간의 사용성 평가는 후속 과제입니다. 발표에는 가상 상담 자료를 사용합니다.

초기 버전 이후에는 실제 사용자의 의견을 받아 캡처 인식과 질문 연결 정확도를 개선할 예정입니다. 이후 배송·예약·구독 등 상담 분야 확대, 사용자가 제공한 통화 녹취의 텍스트 분석, 일정 알림 연동을 검토합니다. 사용자에게 업체의 답변을 받는 것뿐 아니라 실제 문제 해결까지 필요한 확인 과정을 지원하는 서비스로 발전시키고자 합니다.

### Issue tracker

### Domain docs

프로젝트 전체가 하나의 용어집을 공유하는 단일 컨텍스트 구조를 사용합니다. 공통 용어는 루트의 `GLOSSARY.md`, 주요 설계 결정은 `docs/adr/`에 기록합니다. 상세 규칙은 [도메인 문서 설정](docs/agents/domain.md)을 따릅니다.

용어집과 설계 결정 문서는 용어나 결정이 확정될 때 생성합니다. 아직 파일이 없으면 그대로 작업을 진행합니다.

### 설정 유지 관리

에이전트 작업을 시작할 때 이 섹션과 연결된 설정 문서를 참조합니다. 설정을 바꾸려면 `docs/agents/`의 문서를 직접 수정하면 됩니다.
