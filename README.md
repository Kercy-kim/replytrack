# ReplyTrack

> 바쁜 일상 속 문의 내용과 진행 상황을 정리하고, 다음 행동부터 해결 확인까지 이어주는 AI 웹 서비스

과제 제출을 위한 프로젝트 기획과 구현 현황을 정리한 문서입니다. **웹 서비스로 개발·시연**하며 별도의 모바일·데스크톱 앱은 만들지 않습니다. 2026-11-16 기준으로 구현된 기능, 추가 개발할 기능, 검증이 남은 항목을 구분합니다.

**발표 준비:** [5분 발표 구성·대본·과제 항목 대응](docs/PRESENTATION.md) · [30초 시연 안내](docs/DEMO.md) · [결과 재생 설계·최초 검증](docs/PRESENTATION-READINESS.md). 별도 발표 주소 `/presentation`에서 사전 실행한 실제 모델 결과를 확인할 수 있습니다.

**마무리:** [최신 시연·테스트 결과와 발표 직전 준비](docs/FINAL-CHECK.md)에서 실행 순서, 핵심 기능 네 가지, 문제 발생 시 대체 시연 방법을 확인할 수 있습니다.

**발표 대본:** [설명 4분 + 시연 30초](docs/PRESENTATION-4MIN-SCRIPT.md)를 기준으로 연습하면 5분 제한에서 전환 여유 30초를 남길 수 있습니다. 현재 재생 원본의 실제 작업 합계는 150.2초이며, 30초는 결과 설명 시간입니다.

**화면 사용:** 개별 문의 상단의 **문의 진행 요약**에서 내가 확인할 질문, 업체 답변·처리 대기, 내가 할 일·결과 확인을 보고 관련 내용으로 바로 이동합니다. 여러 문의는 **내 문의함**에서 첫 문의 미리보기와 검색·필터로 찾아볼 수 있습니다. 첫 화면과 메뉴는 실제 문의 등록·관리에 집중하며, 예제 생성 버튼과 발표용 링크는 표시하지 않습니다. 발표 결과는 `/presentation` 주소로 직접 엽니다. 재문의는 **답장 작성** 탭, 삭제는 **문의 관리**에서 이용합니다. [문의 정리 화면 검증](docs/INQUIRY-WORKSPACE.md) · [기존 가독성 개선 검증](docs/UI-REFINEMENT.md).

## 1. 프로젝트 개요

ReplyTrack은 **바쁜 일상에서 고객센터에 문의하고, 답변을 확인하고, 필요한 자료를 다시 보내는 과정을 이어가기 어려운 일반 사용자**를 위한 AI 문의 관리 서비스입니다. 온라인 쇼핑뿐 아니라 이메일 문의, 계정 복구, 영어로 주고받는 문의까지 다루는 것을 목표로 합니다. 긴 대화에서 무엇을 물었고 어디까지 답변받았는지, 내가 무엇을 해야 하고 상대방의 어떤 처리를 기다리는지를 원문 근거와 함께 정리합니다.

문의는 한 번 보내는 것으로 끝나지 않는 경우가 많습니다. 일이나 개인 일정으로 며칠 뒤 답변을 열면 앞선 내용을 다시 읽어야 하고, “아, 이것도 보내야 했는데”라며 추가 자료나 질문을 뒤늦게 떠올리기도 합니다. 계정 복구에 필요한 자료를 일부만 제출하거나, 영어 답변에서 제출 조건과 기한을 놓치거나, “접수했습니다”를 실제 해결로 오해할 수도 있습니다. ReplyTrack은 바쁜 일상에서 문의의 진행 상황을 다시 파악해야 하는 부담과, 보내야 할 자료나 확인할 내용을 놓치는 불편을 줄이고자 만들었습니다. 문의 내용과 답변, 남은 질문과 해야 할 일을 함께 정리해 사용자가 문의를 이어갈 수 있도록 돕습니다.

**기획하는 전체 흐름:** 문의·답변 등록 → 질문별 상태와 요구사항 분석 → 지금 내가 할 일·상대방 대기 확인 → 새 답변 반영·재문의 → 실제 해결 결과 직접 확인. 공식 참고 안내는 출처와 조건이 확인된 경우에만 보조로 표시합니다.

**현재 구현 범위:** 문의 등록, 질문별 상태·요구사항 분석, 한국어 설명·영어 재문의, 새 답변 전후 비교와 진행 요약을 제공하는 로컬 웹 시제품입니다. 문의처와 주제가 확인되면 공식 사이트의 본문을 별도로 조회하고 AI가 관련성·조건·원문 근거를 검토합니다. 통과한 안내만 문의 상세에 표시하며 불확실·검색 실패·상담 답변과 충돌한 경우 생략합니다. 현재 SSG 일반 상품과 Google·Microsoft·Apple 계정 복구를 지원하며, 모든 사이트를 검색하는 기능은 아닙니다. 공식 안내는 질문 상태·업체 답변·처리 완료로 저장하지 않으며 새 답변 분석을 기다리게 하지 않습니다.

핵심 기능과 입력→처리→출력은 4절, 생성형 AI의 역할과 검증 원칙은 8절에 정리합니다. 실행 방법과 과거 평가 기록은 문서 뒤의 부록에서 확인할 수 있습니다.

**이메일 문의 구현:** 본문·캡처 직접 등록, 발신자·날짜·인용 중복 검토, 영어 답변의 한국어 설명, 한국어/영어 재문의 초안, 새 이메일 반영을 제공합니다. 계정 복구의 자료 요청·심사·복구 안내도 기존 질문·할 일·약속 구조로 관리합니다. 메일함 연결·자동 수집·발송은 구현하지 않았습니다. 새 기능의 검증 범위는 [이메일 검증 기록](docs/EMAIL-INQUIRIES-VALIDATION.md), 기존 환불·교환 범위에서의 확장 결정은 [ADR 0017](docs/adr/0017-email-inquiries.md)에 기록합니다. 기존 쇼핑 평가 수치를 이메일 성능으로 해석하지 않습니다.

## 2. 개발 목적

- 바쁜 사용자가 문의를 다시 열었을 때 앞선 대화를 모두 읽지 않고 진행 상황과 다음 행동을 파악하도록 돕습니다.
- 온라인 쇼핑·이메일·계정 복구 문의에서 사용자의 상황에 해당하는 조건과 추가로 확인할 정보를 찾도록 돕습니다.
- 여러 질문 중 답변받은 내용과 아직 빠진 내용을 구분합니다.
- 소비자의 행동, 업체가 수행할 처리 약속, AI의 재문의 제안을 구분합니다.
- 새 답변이 오면 바뀐 항목을 보여 주고 남은 내용만 담은 재문의 초안을 제공합니다.
- 업체의 처리 안내와 사용자가 실제 결과를 확인한 상태를 별도로 관리합니다.
- 문의 내용을 한곳에서 확인하여 요청받은 자료나 아직 확인하지 못한 내용을 놓치는 불편을 줄이고자 합니다.
- 영어 문의의 요구사항을 한국어로 이해하고 원문의 조건을 보존한 영어 답장 초안을 작성하도록 돕습니다.

**개발 범위 고정:** 질문별 답변 분석 / 지금 내가 할 일 / 한국어 설명·재문의 작성 / 새 답변 전후 비교의 네 가지에 집중합니다. 인계 요약 생성은 제거했습니다. 기존 저장 요약은 내려받기에 포함하며 기록을 삭제하지 않습니다. 초안 생성 당시 선택 질문을 표시하고, 질문 선택·언어 변경 시 재작성을 안내합니다. [공식 안내 실제 웹 검증·핵심 범위](docs/OFFICIAL-WEB-CORE.md).

[Gmail AI Inbox](https://support.google.com/mail/answer/16845247?hl=en)는 할 일·관련 원문·직접 완료 표시도 제공합니다(베타·제공 조건 있음). [NoReply](https://usenoreply.com/changelog)는 진행 단계와 다음 행동·발송 전 확인을, [Resolver](https://www.resolver.co.uk/resolver-for-businesses-frequently-asked-questions)는 사용자가 관리하는 개인 문의 기록을 설명합니다. 이러한 **다음 행동과 원문을 가까이 두고, 작성 결과를 확인하게 하는 원칙**을 참고했습니다. 이번에는 초안 생성에 사용한 질문을 표시하고 선택·언어 변경 시 재작성을 안내하도록 보완했습니다.

이메일 요약·답장 작성, 할 일 추출, 상담 기록을 기억하기, 다음 대응을 안내하기는 기존 서비스에도 있는 기능입니다. ReplyTrack의 핵심 개선점은 **질문별 답변 충족 여부 → 새 답변에 따른 변화 → 실제 해결 확인을 원문 근거와 연결한 사용 흐름**입니다. 아래 기능은 현재 로컬 시제품에 구현되어 있습니다. 경쟁 서비스에 같은 기능이 없다고 단정하지 않으며, 시간 절감·누락 감소 등의 효과는 실제 사용자 평가로 확인할 계획입니다.

| 개선점 | 사용 상황과 제공 방식 | 검증할 효과 |
| --- | --- | --- |
| 질문별 답변 충족 여부 확인 | 환불액·배송비·기간 중 배송비만 답변받았다면 나머지 질문을 남기고 각각의 답변 상태·판단 이유·원문 근거를 표시합니다. | 미해결 질문을 올바르게 찾는 비율과 소요 시간 |
| 새 답변 반영 전후 비교 | 기존 질문·약속을 같은 ID로 이어 관리하고, 새 답변으로 상태·기한 등이 바뀐 항목과 근거를 표시합니다. | 이전 대화를 다시 읽고 변경 사항을 파악하는 시간과 정확도 |
| 업체 안내와 실제 해결 확인 분리 | “환불 처리했습니다”라는 업체 안내와 사용자의 실제 입금 확인을 별도로 기록합니다. 자료 수신이나 심사 안내만으로 계정 복구를 완료 처리하지 않습니다. | 업체 안내를 실제 완료로 오인하는 비율과 확인 누락 |

소비자의 자료 제출과 업체의 심사·환불 약속을 분리하는 **지금 내가 할 일**은 이 흐름에서 다음 행동을 찾도록 돕습니다. 업체 요청은 별도로 추출·재확인하며, 요청·수행 이력과 질문·약속의 전후 비교는 구분해 보관합니다.

**현재 시연 사례 — 영어 계정 복구 문의:** 필요한 자료와 심사 기간을 함께 물었는데 “구매 영수증의 거래 ID를 보내면 확인 후 심사하겠다”는 답변을 받은 상황입니다. 이후 “거래 ID를 받았고 심사는 영업일 3일 걸린다. 아직 계정은 복구되지 않았다”는 답변을 반영합니다.

| 확인할 항목 | 첫 답변 분석 | 후속 답변 반영·요청 재확인 후 |
| --- | --- | --- |
| 필요한 자료 질문 | 답변 받음 — 구매 영수증의 거래 ID | 답변 받음 유지 |
| 심사 기간 질문 | 부분 답변 — 심사 절차는 있지만 기간은 없음 | 답변 받음 — 영업일 3일, 전후 상태 변화 표시 |
| 지금 내가 할 일 | 거래 ID 제출 요청 | 업체 수신 안내 확인. 사용자 직접 수행 기록과 구분 |
| 실제 계정 복구 | 복구 완료 확인 없음 | 여전히 복구 전. 질문에 답변받아도 실제 해결로 자동 변경하지 않음 |

이 사례는 [실제 OpenAI 실행 기록과 검증 범위](docs/PRESENTATION-READINESS.md)에 근거합니다. `/presentation`은 사전 실행 결과 재생이며, 경쟁 서비스와 같은 입력으로 성능을 비교한 실험은 아닙니다.

**발표용 차별점 설명:** ReplyTrack은 문의의 질문별 답변 충족 여부와 새 답변에 따른 변화를 원문 근거와 함께 추적합니다. 또한 업체의 처리 안내와 사용자의 실제 해결 확인을 구분하여, 바쁜 일상에서도 남은 문의와 진행 상황을 쉽게 파악하도록 돕습니다. 이는 현재 구현한 사용 흐름의 개선 방향이며 시장 유일성이나 경쟁사 대비 성능 우위를 검증한 결과는 아닙니다.

확장 방향에서는 **문의를 중단했다가 다시 이어가는 사용 경험**에 집중합니다. 계정 복구 메일의 자료 제출 요청과 심사 대기를 나누고, 영어 답변의 조건을 한국어 설명과 연결하는 것이 목표입니다. 기본 요구사항 추적과 원문·한국어 설명, 영어 재문의는 구현했으며 다양한 서비스의 복구 절차에 대한 확대 검증은 남아 있습니다. 바쁜 일상에서 진행 상황이나 보낼 내용을 놓치는 불편은 이러한 문의 관리 기능을 만들게 된 배경입니다.

## 3. 예상 사용자

어르신 등 디지털 이용이 익숙하지 않은 사용자도 고려하되, 평가 대상은 쇼핑·이메일·계정 문제 등으로 고객지원에 문의한 경험이 있는 일반 사용자로 계획합니다. 쉬운 표현과 단계별 문답을 개선 목표로 두며, 일반 사용자 평가를 어르신에게 효과가 입증된 결과로 해석하지 않습니다.

원문 근거를 확인한 뒤 `확인하던 내용으로 돌아가기`로 읽던 질문·작성 중인 답장에 복귀할 수 있습니다. 질문 필터와 펼친 근거, 편집 내용도 유지합니다. 분석 결과 질문이 없을 때는 답변 완료로 표시하지 않고 원문 점검을 안내합니다. 이번 전체 점검의 범위·발견 사항·검증 결과는 [완성도 점검](docs/USABILITY-COMPLETENESS.md)에 정리합니다.

문의처와 주제가 확인되면 공식 사이트의 본문을 별도로 조회하고 AI가 관련성·조건·원문 근거를 검토합니다. 통과한 안내만 문의 상세에 표시하며 불확실·검색 실패·상담 답변과 충돌한 경우 생략합니다. 현재 SSG 일반 상품과 Google·Microsoft·Apple 계정 복구를 지원하며, 모든 사이트를 검색하는 기능은 아닙니다. 공식 안내는 질문 상태·업체 답변·처리 완료로 저장하지 않으며 새 답변 분석을 기다리게 하지 않습니다.

### 답변·처리 상태 기준

답변 상태는 **미답변·부분 답변·답변 대기·답변 받음·확인 필요**로 구분합니다. 사용자는 원문 근거와 판정 이유를 확인하고 직접 수정할 수 있습니다.

| 상태 | 구분 기준 | 예시 |
| --- | --- | --- |
| 미답변 | 해당 질문에 관련된 안내 자체가 없음. 인사만 하거나 다른 문제를 안내한 경우 포함 | 반품 배송비 부담 주체를 물었는데 인사만 받음 |
| 부분 답변 | 같은 문제의 방법·조건·일부 정보는 있지만 요청한 개별 결과나 전체 범위는 빠져 있음 | 교환 접수 여부를 물었는데 접수 방법만 안내받음 |
| 확인 필요 | 관련 응답은 있지만 실질 정보 없이 미정이라고 하거나, 모호함·충돌·근거 검증 실패로 직접 확인이 필요함 | 환불액을 물었는데 아직 안내할 정보가 없다는 답을 받음 |

남은 정보를 나중에 안내하겠다는 명시적 약속이 있으면 **답변 대기**, 요구한 정보가 모두 제공되면 **답변 받음**입니다. 최신 정정과 충돌, 부분 정보와 향후 안내 약속이 함께 있을 때의 우선순위는 [상태 판정 기준](docs/adr/0006-question-status-boundaries.md)에 정리했습니다. 정보 미정이나 방법 안내도 해당 업체 답변을 근거로 남깁니다.

처리 상태는 답변 상태와 별도로 **처리 약속·업체의 처리 안내·사용자 확인 완료**를 관리합니다. 기한이 명시되지 않았거나 기준 날짜가 불분명하면 기한 미정으로 남깁니다. 한국 시간 기준으로 오늘까지·기한 지남을 표시하되, 기한 경과를 처리 실패로 단정하지 않습니다. 업체의 답변만으로 실제 처리 완료를 확정하지 않습니다.

초기 시제품의 입력 방식은 텍스트 붙여넣기와 대화 캡처 업로드입니다. 재문의는 초안을 확인하고 복사하는 방식으로 제공하며, 법적 책임이나 보상 가능성을 판정하는 기능은 초기 범위에 포함하지 않습니다.

## 5. 간단한 사용 예시

### 현재 구현으로 시연할 수 있는 흐름

다음은 특정 쇼핑몰의 실제 정책이 아닌 **가상의 환불 상담 사례**입니다.

1. 사용자가 불량 이어폰의 환불 금액, 환불 소요 기간, 반품 배송비 부담 주체를 묻는 상담을 등록합니다.
2. 업체가 “반품 입고 후 환불은 3~5영업일 정도 소요됩니다. 환불 금액은 검수 후 안내하겠습니다. 내일까지 불량 사진을 보내 주세요”라고 답합니다.
3. **지금 내가 할 일**에서 사진 제출은 업체 요청, 배송비 재문의는 AI 제안, 환불액 안내는 업체 대기로 구분합니다. “내일까지”는 사진 제출의 기한이며 환불 기한으로 바꾸지 않습니다.
4. 사용자가 실제로 사진을 제출한 뒤 수행 표시를 합니다. 질문·처리 약속이 환불 완료로 바뀌지는 않습니다.
5. “사진 확인했습니다. 반품 배송비는 업체에서 부담하며, 내일까지 환불 금액을 안내하겠습니다”라는 새 답변을 반영합니다. 배송비는 미답변 → 답변 받음, 안내 기한은 미정 → 날짜 확정으로 바뀝니다.
6. 업체 요청을 다시 확인하면 사진의 수신 안내가 반영되고 이전 직접 수행 표시도 유지됩니다. 이후 업체가 결제 취소를 안내하더라도 사용자는 실제 입금·결제 취소 결과를 별도로 확인합니다.

웹 예제 버튼은 준비된 가상 데이터를 사용하며 **AI API를 호출하지 않는다고 표시**합니다. 실제 상담에서는 질문 분석과 업체 요청 확인을 각각 실행합니다. 상대 날짜는 실제 상담 날짜가 있어야 계산하고 지원하지 않는 표현은 미정으로 남깁니다. 기존 A/S 예제와 저장 상담도 계속 사용할 수 있습니다.

### 관련 공식 안내

문의처와 주제가 확인되면 공식 사이트의 본문을 별도로 조회하고 AI가 관련성·조건·원문 근거를 검토합니다. 통과한 안내만 문의 상세에 표시하며 불확실·검색 실패·상담 답변과 충돌한 경우 생략합니다. 현재 SSG 일반 상품과 Google·Microsoft·Apple 계정 복구를 지원하며, 모든 사이트를 검색하는 기능은 아닙니다. 공식 안내는 질문 상태·업체 답변·처리 완료로 저장하지 않으며 새 답변 분석을 기다리게 하지 않습니다.

공식 안내가 있으면 `관련 공식 안내`를 펼쳐 원문 인용·공식 출처·조회 날짜를 확인합니다. 자료가 없으면 안내 영역 자체를 표시하지 않습니다.

### 이메일 문의 사용하기

실제 AI 연결 후 `새 상담 시작하기`에서 문의 유형을 `이메일 문의`로 선택합니다. 다음은 특정 서비스의 실제 정책이 아닌 가상 계정 복구 사례입니다.

1. 계정 복구를 위해 보낸 이메일과 받은 답변을 헤더와 함께 붙여넣거나 캡처 한 장(PNG/JPEG/WebP, 4MB 이하)을 등록합니다. 영어 캡처는 `캡처 언어: 영어`를 선택합니다. 전송 전 가림·OCR 결과를 확인하고, 다음 화면에서 발신자·순서·날짜를 검토합니다. 발신자가 불명확하면 직접 선택해야 저장됩니다. 가상의 답변은 “Please provide the transaction ID. After we verify it, we will update you on the recovery request.”입니다.
2. 질문 분석 후 `한국어 설명 보기`를 누르면 AI가 한국어로 “거래 번호 제출이 필요하며, 확인 후 복구 요청에 대한 안내가 올 예정”이라고 설명하고 영어 근거를 연결합니다. **거래 번호 제출은 내 할 일, 검증 후 안내는 상대방 대기, 안내 기한은 미정**으로 표시합니다.
3. 사용자는 일이 바빠 답변 확인을 중단했다가 나중에 다시 기록을 엽니다. 대화 전체를 다시 읽는 대신 남은 제출 요구사항과 답변 대기 항목을 확인합니다.
4. `답장 작성`에서 남은 질문과 `답장 언어: English · 영어`를 선택해 초안을 만들고, 사용자가 검토한 뒤 실제 메일 서비스에서 자료와 함께 직접 보냅니다. 초안이 실제 첨부·발송을 보장하지는 않습니다.
5. `새 답변 추가`에서 새 메일을 붙여넣거나 캡처로 가져옵니다. 검토 후 저장하면 질문·약속 전후 비교가 갱신됩니다. 한국어 설명과 업체 요청은 각각 다시 확인해 새 원문을 반영합니다. 복구 안내가 와도 실제 로그인 성공 여부는 사용자가 별도로 확인합니다.

계정 복구 기능은 받은 요구사항을 이해하고 진행 상황을 관리하는 것이 목적입니다. 서비스별 복구 정책을 임의로 만들거나 계정을 직접 복구하지 않습니다. 민감정보 입력 안내·가림 범위는 확장 개발에서 보완하며, 현재 전화번호·주소 가림을 모든 계정 정보의 보호로 해석하지 않습니다.

### 30초 시연 구성

별도 발표 주소 `/presentation`을 열면, 가상 계정 복구 문의를 실제 OpenAI API로 실행한 결과를 네 장면으로 재생합니다. AI가 생성한 설명·초안과 상태를 그대로 사용하고 원본 기록 해시를 연결합니다.

| 시간 | 화면 조작 | 보여 줄 핵심 |
| --- | --- | --- |
| 0~6초 | 문의 등록 | 필요한 자료와 검토 기간을 물은 영어 원문 |
| 6~14초 | 설명과 할 일 | 한국어 설명, 거래 ID 제출 요청, 기간 질문의 부분 답변 상태 |
| 14~21초 | 영어 재문의 | 남은 기간 질문만 담은 실제 AI 초안 |
| 21~30초 | 새 답변 비교 | 검토 기간이 답변 받음으로, 자료 요청이 수신 안내로 변화. 실제 복구는 아직 전 |

**실제 AI 결과의 사전 실행·재생**임을 모든 장면에 표시합니다. 재생 중에는 API를 호출하거나 상담 기록을 변경하지 않습니다. 최신 기록의 실제 작업 시간 합계는 약 150.2초로, 30초는 결과를 설명하는 시간입니다. API 응답 시간이 30초라는 뜻이 아닙니다. 원문·모델·실제 실행 시간·검토된 결과 JSON을 확인할 수 있습니다. 기존 가상 기록은 삭제하지 않고 별도로 표시하며, 새 가상 기록을 만드는 버튼은 일반 화면에서 제공하지 않습니다.

5분 발표의 문제·사용자·핵심 기능·AI 역할·테스트 구성은 [발표 대본](docs/PRESENTATION.md), 조작은 [시연 안내](docs/DEMO.md), 최신 검증은 [발표 준비 검증](docs/PRESENTATION-READINESS.md)에 정리합니다.

**공식 참고 안내 흐름:** 등록된 문의 → 확인된 문의처·주제 → 공식 본문 조회 → 원문·적용 조건 검토 → 통과한 안내만 별도 표시.

서버는 AI가 인용한 문장·발화자가 원문에 존재하는지 검사합니다. 추가 답변은 분석 전에 저장하고 버전 검사로 오래된 분석의 덮어쓰기를 막습니다. 실패·취소 시 기존 기록을 보존합니다. 현재 설계는 [ADR 0001](docs/adr/0001-local-mvp.md), 할 일의 구분은 [ADR 0015](docs/adr/0015-refund-next-actions.md), 공식 참고 안내 전환은 [ADR 0022](docs/adr/0022-presentation-core-focus.md)에 기록했습니다.

## 8. AI 활용방안

### 생성형 AI가 필요한 이유

사용자의 “돈을 돌려받고 싶어요”라는 표현은 주문 취소·반품·환불 지연 등 여러 상황을 가리킬 수 있습니다. 업체 답변도 조건, 선행 행동, 처리 약속을 한 문장에 섞어 전달합니다. 생성형 AI는 이런 표현의 의미와 앞뒤 관계를 해석하고, 필요한 확인 질문·판정 이유·행동 설명·재문의 문장을 생성하는 데 활용합니다.

예를 들어 “내일까지 사진을 보내 주세요. 확인 후 환불 금액을 안내하겠습니다”를 **사진 제출 / 소비자 기한: 내일까지 / 업체 약속: 확인 후 금액 안내 / 아직 모르는 것: 환불 금액과 실제 환불 시점**으로 분리합니다. 문장에 없는 기한이나 실제 완료 여부는 만들어 내지 않습니다.

확장할 이메일·계정 복구 문의에서도 같은 자료가 “구매 증빙”, “결제 내역”, “proof of purchase”처럼 다르게 표현되고, 제출 조건과 심사 안내가 여러 답장에 흩어질 수 있습니다. AI로 의미와 문맥을 연결해 요구사항을 정리하고, 영어 설명·답장의 의미를 생성 후 검토합니다. 기록 저장·수행 표시·기한 계산은 일반 코드가 담당합니다.

| 담당 | 역할 |
| --- | --- |
| 생성형 AI | 의도·조건·행동 주체 해석, 질문·답변 연결, 새 답변 반영, 설명·재문의 생성, FAQ 안내 생성·근거 및 조건의 의미 검토 |
| 일반 코드·OCR | 이미지의 로컬 문자 인식, 전화번호·주소 가림, 날짜 계산, 원문 인용 검증, 변경 비교, 기록 저장·취소·검색 |
| 사용자 | 인식 원문·날짜와 판정 검토, 초안 수정, 요청받은 행동의 직접 수행 표시, 실제 처리 결과 확인 |

### 근거와 오류 처리

- 현재 분석은 상담 원문을 근거로 삼고, AI 제안과 사용자가 편집한 초안을 업체가 말한 사실로 취급하지 않습니다.
- 업체 요청은 별도 생성·의미 검토 후 저장하며 실패·취소 시 이전 목록을 유지합니다. 수행 표시만으로 환불·교환 완료를 확정하지 않습니다.
- 공식 안내는 현재 조회한 본문과 출처·조회 날짜를 연결하며 인용·의미 검토 실패 시 표시하지 않습니다. 확인되지 않은 문의처나 조건을 추측하지 않습니다. AI 검토가 완전한 정확성을 보장하지는 않습니다.
- 기존 실제 AI 평가, 새 기능의 가상 응답 테스트, 실제 사용자 평가를 구분합니다. 기존 상담 분석 평가 결과를 새 FAQ 안내의 정확도로 사용하지 않습니다.
- 이메일·계정 복구·영어 문의는 새 사례로 별도 평가합니다. 원문에 없는 제출 요구나 기한을 만들지 않는지, 번역에서 조건·부정 표현이 바뀌지 않는지 확인할 계획입니다.

현재 모델·호출 방식과 상세 검증 경계는 부록의 AI 구현 메모에 보존합니다.

## 9. 개발 일정

기획·설계·구현·검증·발표를 포함한 **총 5주 계획**입니다. 주차별 목표이며 현재 완료 이력을 뜻하지 않습니다. 구현 여부는 4절의 현황을 기준으로 합니다.

| 기간 | 주요 작업 | 결과물 |
| --- | --- | --- |
| 1주차 | 바쁜 사용자의 문의 중단·누락 문제 정의, 쇼핑·이메일·계정 복구·영어 사례와 평가 기준 선정, 기존 서비스 비교 | 기획서, 기능 명세, 화면·데이터 설계, 구현·확장 범위 구분 |
| 2주차 | 텍스트·캡처·이메일 본문 직접 등록, 개인정보 가림, 질문별 답변·요구사항·약속 분석, 문의처별 공식 근거 연결 | 상담 등록·근거 기반 분석 시제품, 공식 참고 안내 |
| 3주차 | 할 일·새 답변 비교·재문의 연결, 계정 복구 요구사항 관리와 영어 설명·답장 지원 | 일반 문의까지 이어지는 핵심 흐름, 분야별 평가 사례 |
| 4주차 | 사용자별 기록 분리, 웹 배포, 전체 흐름 통합 검증과 체험 모집 | 배포 시제품, 기록 분리·전체 흐름 검증 결과 |
| 5주차 | 기존 분야 회귀와 새 분야·영어 실제 AI 평가, 실제 사용자 10명 이상·설문 10문항 이상 평가, 오류 수정·시연·발표 준비 | 분야별 평가 보고서, 최종 시연 버전, 제출 자료 |

위 일정은 과제의 5주 계획입니다. 실제 3일 시연 준비에서는 기존 핵심 흐름을 유지하고, 본문 직접 입력을 이용한 이메일·계정 복구 예제와 영어 지원의 최소 흐름을 우선 개발·검증합니다. 메일함 자동 연동은 후속 후보로 두며, 확장 기능·배포도 검증이 끝나기 전까지 완료로 표시하지 않습니다.

## 10. 기대 효과 및 향후 계획

사용자가 긴 안내와 상담에서 남은 질문·행동을 찾는 시간과, 중단했던 문의의 맥락을 다시 파악하는 부담을 줄일 것으로 기대합니다. 추가 질문·자료를 잊거나 영어 답변의 조건을 놓치는 일을 줄이고, 업체 답변을 실제 처리 완료로 오인하지 않도록 돕는 것이 목표입니다. 이는 검증할 목표이며 현재 입증된 사용자 성과가 아닙니다.

### 사용자 평가 계획

쇼핑·이메일·계정 문제 등으로 고객지원에 문의한 경험이 있는 **실제 사용자 10명 이상**에게 배포본을 사용하도록 하고, **설문 10문항 이상**으로 만족도를 정량 평가할 계획입니다. 영어 문의 경험과 사례 유형을 구분해 보고하며, 가상 상담 10건이나 자동 테스트를 실제 사용자 10명으로 계산하지 않습니다.

| 과제 | 비교 방법 | 측정 지표 |
| --- | --- | --- |
| 내 상황에 필요한 안내 찾기 | 공식 FAQ 직접 탐색과 FAQ 안내 기능 비교(개발 후) | 적용 조건·다음 행동 정답률, 소요 시간 |
| 내가 할 일과 업체 대기 구분하기 | 상담 원문만 읽기와 ReplyTrack 사용 비교 | 행동 주체·기한 정답률, 도움 요청 횟수 |
| 새 답변에서 해결·미해결 항목 찾기 | 비슷한 난도의 서로 다른 상담으로 비교 | 미해결 질문 정답률, 소요 시간, 처리 완료 오인 비율 |
| 중단한 문의 이어가기·추가 제출 챙기기 | 일정 시간 뒤 원문만 다시 읽기와 기록·할 일 확인 비교 | 진행 상황 파악 시간, 요청받은 제출 항목 누락률 |
| 영어 계정 복구 답변 이해·회신하기 | 원문 직접 읽기와 한국어 설명·영어 초안 이용 비교(개발 후) | 요구사항·조건·기한 이해도, 답장 내용 누락·의미 변경 비율 |

같은 사례를 반복해서 답을 외우는 효과를 줄이기 위해 사례와 이용 순서를 나눕니다. 설문은 필요성, 시작 편의, 입력 편의, 추가 질문 이해, 안내 이해, 조건 이해, 근거 확인, 할 일 구분, 응답 속도, 재사용 의향의 10개 항목을 기본으로 합니다. 표본·평가 방법·실패 사례를 함께 보고하고, 측정하지 않은 실제 환불 성공률이나 어르신 대상 효과로 확대 해석하지 않습니다.

### 후속 우선순위

1. 문의 분석·할 일·공식 참고 안내의 품질을 확인하며, 화면과 프롬프트를 일반 문의에도 맞게 확장합니다.
2. 구현한 이메일·계정 복구 흐름과 영어 설명·답장을 더 다양한 실제 AI 평가 사례로 검증하고, 요구사항·조건·언어의 정확도를 개선합니다.
3. 기존 기록·남은 질문·할 일을 쉽게 파악할 수 있도록 사용성을 개선하여 중단했던 문의를 다시 이어가는 부담을 줄입니다.
4. 사용자별 기록 분리를 포함해 웹을 배포하고 실제 이용자의 과제 수행·만족도를 평가합니다. 메일함 연동과 지원 서비스 확대는 그 결과에 따라 검토합니다.

현재 Google 로그인·메일함 자동 수집·자동 발송·리마인더는 구현되지 않았습니다. 영어 설명·재문의는 구현했으며, 메일함 연결은 후속 후보입니다. 실제 문의 발송은 사용자가 원래 서비스에서 직접 수행합니다. 기존 A/S·배송·구독 상담 기록은 보존하며, 아래의 과거 평가를 이메일·계정 복구·영어 문의나 새 FAQ 기능의 성능으로 바꾸어 해석하지 않습니다.

**이메일 추가 후 최신 검증(2026-11-15):** 배송·환불·구독 전체 48건을 실제 API로 재평가하고 경계 판정·처리 통보 누락을 보완했습니다. 최종 48/48건, 질문 상태 71/71회, 약속·기한 22/22회, 지정 초안 13건을 통과했습니다. 실제 이메일 2건, 자동 테스트 199개, 문법 검사 98개 파일, Chrome 이메일·30초 발표 흐름도 확인했습니다. 중간 실패와 범위는 [전체 회귀·발표 검증](docs/EMAIL-REGRESSION-DEMO.md)에 기록합니다.

아래 수치는 각 보고서에 기록된 과거 검증 결과입니다. 기존 상담 분석에 대한 수치이며, 이번 공식 FAQ 안내 검증 결과는 별도 문서에 기록합니다.

### 실행하기

**Node.js 24 이상과 npm**이 필요합니다. 최초 실행 또는 의존성 변경 후 `npm ci`로 로컬 캡처 인식 엔진과 한국어·영어 모델을 설치합니다. 웹 빌드는 필요하지 않습니다.

```powershell
npm ci
node server.mjs
```

브라우저에서 [http://127.0.0.1:3100](http://127.0.0.1:3100)을 엽니다.

- **추가 환불 시연:** `예제 상담 열기` → 사진 제출 요청·수행 기한 확인 → `수행했어요` → 질문별 상태 확인 → `답장 작성` → 초안 생성 → `예제 답변 추가하기` → `환불 안내 시연하기` → 실제 결과 직접 확인. 예제는 준비된 가상 데이터로 동작하며 AI API를 호출하지 않는다고 화면에 표시합니다.
- **실제 AI 분석:** `AI 연결 설정` → `저장하고 연결 점검`으로 실제 키·모델·응답 형식을 확인합니다. 키는 서버 메모리에만 유지됩니다. `새 상담 시작하기` → 텍스트·캡처 입력 → `개인정보 가리고 확인` → 마스킹 결과 검토 → `확인한 내용으로 AI 대화 읽기` → 발화자·원문·날짜 확인 → 분석 순서입니다. 직접 메시지를 나누어 입력할 수도 있습니다.
- **진행·취소:** 연결 확인, 캡처 읽기, 분석, 근거 검증, 의미 검토, 수정 등 실제 서버 단계와 경과 시간을 표시합니다. `작업 취소`는 서버·AI 요청을 중단하며 늦게 도착한 결과를 저장하지 않습니다. 입력과 기존 기록·편집 초안은 유지됩니다. 추가 메시지를 이미 저장했다면 그 메시지도 남아 재분석할 수 있습니다. 취소 전에 완료된 작업은 완료 결과를 반영했다고 안내합니다.
- **기본 개인정보 가림:** 한국 전화번호·도로명·지번 주소를 외부 AI 전송 전에 가립니다. 캡처는 로컬 OCR로 읽으며 원본 이미지는 외부로 보내지 않습니다. 자동 탐지는 완벽하지 않으므로 전송 전 미리보기에서 누락·인식 오류와 이름·계좌번호 등을 확인합니다. 새 상담·추가 메시지는 가린 텍스트로 저장합니다.
- **지금 내가 할 일:** 질문 확인표 상단에서 업체 요청, AI 재문의 제안, 직접 확인할 처리 결과, 업체 안내 대기를 구분합니다. `업체 요청 확인하기`는 원문에서 소비자 행동을 추출하고 별도 AI 검토 후 저장합니다. 조건·기한과 원문 근거를 표시하며, `수행했어요`·취소는 기록에 저장됩니다. 새 메시지 이후에는 이전 요청을 명시하고 갱신 전 수행 표시를 막습니다. 질문·약속·초안은 할 일 작업의 실패·취소로 바뀌지 않습니다. 기존 질문 분석에 자동 호출을 추가하지 않습니다.
- **환경변수 사용:** `.env.example`을 참고해 로컬 `.env`에 `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정할 수 있습니다. 기본 모델은 `gpt-5-mini`입니다. `.env`와 상담 데이터는 Git에서 제외합니다. API 키를 README나 소스 코드에 넣지 않습니다.
- **저장:** 상담 원문과 분석 결과는 `data/replytrack.sqlite`에 저장됩니다. 재시작해도 기록이 유지되며, `내려받기`로 Markdown을 내려받을 수 있습니다. 초안을 직접 고친 뒤 `편집 저장`을 누르면 새로고침 후에도 유지됩니다. 원본 캡처는 저장하지 않습니다.
- **입력 이어가기:** 새 상담의 제목·대화·선택한 캡처·가림 편집·검토 날짜는 이 탭을 열어 둔 동안 유지됩니다. 설정을 마치거나 창을 닫았다 다시 열어도 같은 단계로 돌아옵니다. 새로고침·탭 종료 시에는 유실 경고를 표시하며, 저장 전 원문을 브라우저 저장소에 따로 보관하지 않습니다.
- **기다리는 동안:** 상담 분석·초안 생성 중에도 다른 상담, 질문·원문·이력을 조회하고 기존 초안을 복사·내려받을 수 있습니다. 변경과 새 AI 요청은 현재 작업 종료 후 가능합니다. 작업 대상 상담은 진행 영역에 표시되며, 완료되어도 현재 보고 있는 다른 상담으로 결과가 섞이지 않습니다.
- **새 답변 추가:** 실제 상담 상단의 `새 답변 추가`로 바로 이어 붙입니다. 모바일 날짜·시간은 전체 너비로 표시하고, 상태 배지와 근거 글자를 크게 읽을 수 있도록 조정했습니다. 변경과 검증 범위는 [웹 사용성 개선 기록](docs/UI-USABILITY.md)에 정리했습니다.

[새 상담 평가 보고서](docs/UNSEEN-EVALUATION.md)와 [상태 기준 재평가 보고서](docs/STATUS-BOUNDARY-EVALUATION.md)에 초기 평가와 수정 과정을 기록했습니다. 이후 전체 회귀에서는 기존 배송 17·환불 17·구독 14건을 실제 API로 다시 실행했습니다. 기간 원문 가림, 부분 답변 처리, 인계 질문 확대·담당자 추정, 근거 없는 설명을 보완한 최종 수정본에서 **48/48건·55/55 분석 단계·질문 상태 및 근거 71/71·약속/기한 22/22**가 통과했습니다. 지정 재문의·인계 13회와 별도 인계 18회의 원문 대조, 정상·오류 초안 검토 대조 18개도 통과했습니다.

[전체 AI 회귀 보고서](docs/FULL-AI-REGRESSION.md)에 실패·중단한 실행과 최종 결과, 소스 해시 검증 및 남은 설명 문구의 개선 여지를 구분했습니다. 정답 작성과 원문 대조는 개발 에이전트가 수행했으며, 고정 가상 자료의 결과가 실제 사용자 전체의 정확도나 비용 절감을 입증하지는 않습니다. 외부 사람 검수와 남은 질문을 찾는 시간의 사용성 평가는 후속 과제입니다. 발표에는 가상 상담 자료를 사용합니다.

후속 [판정 이유 개선 평가](docs/REASON-SCOPE-EVALUATION.md)에서는 묻지 않은 부족 사항과 판정 과정 해설을 줄여, 같은 질문 71개의 이유가 평균 **67.5자→34.0자(49.7% 감소)**로 짧아졌습니다. 기존 상담 **48/48건·질문 상태/근거 71/71·약속/기한 22/22**를 유지했고 상세 경로·시각·예외 보존 대조도 통과했습니다. 근거 인용 누락, 재문의의 추가 절차 질문, 예약 가능성과 실제 상태의 혼동도 보완했습니다. 자동 테스트는 **123개**를 통과했습니다. 문구 보조 검사의 오탐은 원본 출력을 수정하지 않고 별도 재채점했습니다. 다만 이번 비교의 총 API 토큰은 **34.6% 증가**했고 초안 p95도 늘었으므로, 표시 문장 간결화를 처리 비용·속도 개선으로 해석하지 않습니다. 기존 저장 상담에는 다시 분석할 때 적용됩니다.

## 부록 B. AI 구현 메모와 참고 자료

AI의 답변 충족 판정은 업체 설명의 사실 여부나 법적 타당성을 보증하지 않습니다. 근거가 부족하면 확인 필요로 남기고 사용자가 수정할 수 있습니다. 현재는 `gpt-5-mini`와 JSON 스키마를 사용하는 Structured Outputs로 분석 구조를 고정하고, 서버에서 근거 참조와 초안의 숫자·기한을 추가 검증합니다. 이 검증만으로 모든 의미적 오류나 환각을 방지할 수 있는 것은 아닙니다. 여러 모델의 한국어 품질·비용·응답 시간 비교는 후속 평가로 진행합니다.

실제 재문의는 선택한 질문에서 **아직 답변받지 못한 정보만** 요청합니다. 부분 답변에서 이미 받은 금액·서류·안내 기한을 되묻거나, AI가 만든 제목의 부연을 새로운 질문으로 추가하지 않습니다. 미정인 날짜·기간, 실제로 빠진 서류, 해소되지 않은 상충은 유지합니다. 한 항목은 정중한 한 문장으로 작성하며 불필요한 서두와 반복을 줄입니다.

생성 뒤 소비자 관점·남은 선택 질문의 누락·원문 사실·추가 요청·답변 중복의 다섯 기준으로 AI가 검토하고 필요하면 한 번만 수정합니다. 첫 생성은 low, 검토·수정은 medium이며 보통 2회, 수정 시 최대 4회의 API 호출이 발생합니다. 검토 실패 시 기존 초안을 보존하고, AI의 추정 설명을 원문 사실처럼 전달하지 않습니다. 새로 작성하는 초안부터 적용하며 기존 편집본을 자동으로 덮어쓰지 않습니다. 실제 API 평가와 웹 검증은 [재문의 초안 개선 기록](docs/FOLLOWUP-FOCUS-VALIDATION.md), 결정은 [ADR 0027](docs/adr/0027-focused-followup-scope.md)에 정리합니다.

분석은 최초 질문 추출과 기존 질문 갱신을 구분합니다. 업체 답변만 추가되면 질문 제목·원문·ID를 보존하고 상태·이유·근거·약속을 갱신합니다. 짧고 조건이 없는 일반 상담 갱신에는 집중된 지침과 low를 적용할 수 있습니다. 기존 기한의 정정·철회와 이메일 정정은 medium을 유지합니다. 기존 약속이 있는 짧은 이메일 갱신은 질문 판정과 약속 분석을 병렬 처리하고, 각각 전체 질문 지침·약속 전용 지침을 사용합니다. 두 결과가 모두 검증돼야 한 번에 저장하며 실패·취소 시 이전 결과를 보존합니다. 초기 일반 분석은 기본 low, 초기 이메일과 복잡한 문맥은 medium입니다. [긴 이메일 분석 지연 개선 기록](docs/EMAIL-UPDATE-TAIL-LATENCY.md)에 원인·전후 비교·평가 범위를 정리합니다.

최초 등록에서는 짧고 정정이 없는 문의에 한해 별도 기능인 재문의 문장을 분석과 함께 생성하지 않습니다. 일반 상담은 저장된 약속의 갱신 지침·기한 삭제 출력도 제외하며, 단순 이메일은 기존 약속 지침을 유지합니다. 조건부 이메일은 품질을 위해 출력 축소도 적용하지 않고 기존 경로를 유지합니다. 향후 안내가 포함된 복합 질문이나 여러 업체 메시지는 처음부터 기본 medium을 사용해 low 분석 뒤 중복 재검토가 생기는 경우를 줄입니다. 원문·모델·근거 검증은 유지합니다. [최초 등록·분석 전후 비교와 품질 검증](docs/INITIAL-ANALYSIS-LATENCY.md)에 실패한 후보, 최종 적용 범위와 남은 지연을 구분했습니다.

원문 ID·발화자·실제 인용을 검증하고, 인용·구조 오류는 전체 스키마로 한 번 재검토합니다. 의미 검토는 medium을 유지하며 의심되는 질문과 약속 또는 약속만 다시 생성합니다. 안내 시점과 실제 처리 시점, 실제 누락과 추정한 추가 요건, 일반 심사 기간과 개별 업무 확약을 구분합니다. 철회 근거 없이 기한을 지우는 결과도 재검토하고, 단순 완료 통보는 기한 이력을 유지합니다. 새 날짜로 변경하면 새 기한을 반영하고 대체 날짜 없이 명시적으로 철회할 때만 기한을 제거합니다. 경계 상태·처리 통보 누락 검토와 취소·버전 검사를 유지하며, 재검증 실패 시 이전 기록을 보존합니다. 분석·검토는 일반 경로 최대 4회, 이메일 병렬 경로 최대 5회이며 첫 분석 지연 시 동시 보조 요청은 최대 1개입니다. 확인한 사용량과 미확인 요청 수를 구분합니다. 최신 결정은 [ADR 0026](docs/adr/0026-focused-semantic-review.md), [ADR 0028](docs/adr/0028-parallel-email-update.md), [ADR 0029](docs/adr/0029-initial-analysis-output.md)을 따릅니다.

## Agent skills

### Issue tracker

기획 명세와 구현 작업은 [Kercy-kim/tripsketch-ai의 GitHub Issues](https://github.com/Kercy-kim/tripsketch-ai/issues)에서 관리합니다. 작업 생성·조회·의존 관계에 관한 상세 규칙은 [이슈 관리 설정](docs/agents/issue-tracker.md)을 따릅니다.

연결된 GitHub 도구를 우선 사용하며, GitHub CLI(`gh`)가 설치되고 인증된 환경에서는 CLI도 사용할 수 있습니다.

커밋 메시지와 PR 제목·설명은 한국어로 작성합니다.

### Domain docs

프로젝트 전체가 하나의 용어집을 공유하는 단일 컨텍스트 구조를 사용합니다. 공통 용어는 루트의 `GLOSSARY.md`, 주요 설계 결정은 `docs/adr/`에 기록합니다. 상세 규칙은 [도메인 문서 설정](docs/agents/domain.md)을 따릅니다.

용어집과 설계 결정 문서는 용어나 결정이 확정될 때 생성합니다. 아직 파일이 없으면 그대로 작업을 진행합니다.

### 설정 유지 관리

에이전트 작업을 시작할 때 이 섹션과 연결된 설정 문서를 참조합니다. 설정을 바꾸려면 `docs/agents/`의 문서를 직접 수정하면 됩니다.
