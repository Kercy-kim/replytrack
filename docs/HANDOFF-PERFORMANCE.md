# ReplyTrack 인계 응답 시간 개선

평가일: 2026-11-14. 기준 main은 `1309bb1be35598edfd99d80f5ddfc7b66e4f73f8`이다. 이전 전체 상담 평가에서 인계 중앙값 58.09초·최장 91.22초가 측정되어 인계만 별도로 개선했다.

## 원인과 변경

이전 기록에서 NS03은 첫 초안에 내부 메시지 ID가 들어가 다시 생성했다. NU06과 R03은 재문의 지침이 섞이면서 안내 시점을 새 요청으로 추가했고, 검토가 거절하여 다시 생성·검토했다. 짧은 인계에도 생성 단계의 medium 추론이 오래 걸렸다.

- 인계 전용 지침을 분리하여 문의·현재 유효한 안내·남은 질문만 짧게 정리한다. 정정 순서, 업체 설명과 실제 확인, 철회한 기한과 남은 약속을 구분한다.
- 첫 생성은 low, 검토와 한 번의 수정은 medium으로 실행한다. 이전 ADR 0008의 인계 첫 생성 medium 선택을 실제 품질 비교 후 변경한다.
- 인계 검토는 기존 검토 기준에 질문 범위·미해결 상충·원문 내 허위 작성 지시·소비자 관점 구분을 추가한다. 재문의에서 허용하는 안내 시점 질문을 인계에 새로 넣지 않는다. 정정 없는 상충은 뒤의 답변으로 확정하지 않는다. 자기 계정이나 직접 확인을 고객님/고객이로 서술하는 오류를 거절하되 원문 직접 인용은 허용한다.
- 모델·원문·질문·약속·출처 스키마는 그대로 유지한다. 숫자·기한·내부 ID·담당자 표현 검증과 별도 AI 의미 검토를 생략하지 않는다. 검토 완료 전 표시하지 않으며 실패 시 기존 편집 초안도 보존한다.
- 분석과 재문의의 프롬프트·입력·추론 설정은 변경하지 않는다. 모델 변경, 유료 우선 처리, 결과 캐시로 얻은 수치가 아니다.

설계는 [ADR 0009](adr/0009-handoff-specific-generation.md)에 기록했다.

## 비교 설계

이전 소스를 Git 커밋에서 별도 디렉터리로 고정하고 전후 구현을 동시에 실행 가능한 상태로 둔다. **같은 원문·분석 결과·ID를 양쪽에 제공**하므로 분석 모델의 재실행 변동은 비교에 들어가지 않는다. 이는 분석부터 인계까지의 전체 사용자 흐름이 아닌, 분석을 마친 기록의 인계 생성 비교다.

- 기존 인계 6건(NS03, NR05, NU06, S06, U06, R03)을 각각 두 번, 새로운 합성 기록 H01~H06을 한 번씩 실행한다. 총 12개 기록·18쌍, 전후 각각 18회다.
- 새로운 기록은 조건부 교환, 직접 확인된 처리, 할인 정책과 실제 청구, 원문 내 지시, 날짜 변경, 구독 해제와 환불 문의를 포함한다. 분석 상태는 수동으로 고정한 입력이며 이 새 자료의 분석 정확도를 측정한 것은 아니다.
- [고정 입력과 검토 기준](../evals/handoff-cases.json)은 첫 API 호출 전에 작성했다. 검토 기준은 모델에 보내지 않는다. 메모리 SQLite를 사용하여 실제 사용자 DB에 기록하지 않는다.
- 모델은 전후 모두 `gpt-5-mini-2025-08-07`, 출력 한도 6,500토큰이다. 한 쌍 안에서 전후를 순차 실행하고 쌍마다 AB/BA 순서를 번갈아 배치한다. 작업자 두 개로 API 동시 요청은 최대 2개다.
- 첫 후보는 NS03·NU06의 4쌍과 나머지 14쌍으로 나누어 실행했다. 두 번째 후보도 전체 비교했으나 소비자 관점 오류를 발견해 보완했다. **최종 코드는 기준 main과 18쌍 전체를 새로 실행**했다. 초기 실행의 좋은 결과만 최종 수치에 섞지 않는다.
- 완료 시간은 생성·서버 검증·AI 검토·필요한 수정·저장까지 포함한다. 실패한 요청의 대기 시간도 포함한다. UI 렌더링·OCR·분석 시간은 제외한다.
- 중앙값은 정렬한 관측값의 `floor(n/2)` 위치(짝수이면 가운데 두 값 중 큰 값), p95는 nearest-rank 방식이다. 18회에서 p95는 최댓값이므로 큰 모집단의 안정적인 추정치로 보지 않는다.

## 최종 측정

[최종 원본](../evals/results/handoff/final.json)과 [비교 집계](../evals/results/handoff/comparison.json). 같은 12개 기록에서 전후 각각 18회 실행한 결과이며, 이전 58.09초 수치와는 다른 표본이다.

| 지표 | 기준 main | 개선안 | 변화 |
| --- | ---: | ---: | ---: |
| 인계 완료 중앙값 | 38.018초 | 17.346초 | 54.37% 감소 |
| 인계 완료 p95 | 96.808초 | 51.875초 | 46.41% 감소 |
| 저장 성공 | 17/18회 | 18/18회 | 개선안 실행 실패 없음 |
| 수정 후 저장 | 4회 | 2회 | 검증·수정 절차 유지 |
| API 호출 | 42회 | 39회 | 실패 호출 포함 |
| 양쪽 성공·사용량 확인 가능한 17쌍의 총 토큰 | 111,986 | 80,522 | 28.10% 감소 |

기준 구현의 H06은 67.566초 뒤 `AI_INCOMPLETE`로 실패했다. 이 대기 시간도 위 중앙값·p95에 포함한다. 해당 호출 사용량을 클라이언트에서 받지 못했으므로 **18쌍 전체의 토큰 절감률은 계산하지 않는다.** 개선안 18회 총량은 84,868토큰이며, 17쌍 토큰 비교에서는 H06을 양쪽 모두 제외했다. 이 부분집합에서 기준 중앙값은 36.601초, 개선안은 17.346초다. 실패 사례를 제외한 보조 비교이며 전체 성공률과 혼동하지 않는다.

캐시 입력도 총 토큰에 포함했다. 17쌍의 캐시 입력은 기준 29,696, 개선안 15,488토큰이다. 입력+출력 총량 기준이며 실제 청구액 절감률은 계산하지 않았다. 실패 호출의 과금 여부나 사용량을 0으로 가정하지 않는다.

개선안 NR05 첫 반복은 본문 내부 ID를 서버가 차단해 다시 생성했으며 30.933초가 걸렸다. 기준의 29.125초보다 이 한 쌍은 느렸다. R03 첫 반복은 검토가 '환불 예정일 미정'이라는 단정을 '확인 중'과 답변 대기로 수정하도록 요청하여 51.875초가 걸렸다. 따라서 모든 요청이 빨라졌거나 긴 대기가 사라졌다는 결과는 아니다. 검토·수정을 생략하지 않고 완료 시간 중앙값과 p95를 함께 줄였다는 소규모 관측이다.

## 내용 품질 대조

제품의 검토 통과와 독립적으로 개발 에이전트가 모든 전후 초안을 원문 및 미리 고정한 기준에 대조한다. 내부 검토 AI의 valid 값을 독립 정확도로 사용하지 않으며 외부 사람 검수라고 주장하지 않는다.

개선안은 **18/18개 저장 초안에서 정정·기한·남은 질문·확인 주체·출처를 대조**했다. 아래는 같은 기록의 두 반복을 묶은 결과다. 기준 구현에서 생성된 17개 초안도 대조했고, H06은 초안이 없어 품질 성공으로 세지 않았다.

| NS03 | 2/2 | 위치 확인 완료와 옆 동 1층 경비실 안내. 실제 수령 완료를 주장하지 않음 |

기준 H01은 원래 방문일 질문에 안내 시점 요구를 붙였고, H03은 다음 청구액 외에 할인 적용 여부도 별도 요청했다. 개선안은 남은 질문을 평서문으로 전달한다. 원문에 없는 숫자·직접 확인·담당자 신원은 최종 인계에 추가하지 않았다. 사용한 사실·과거 안내의 메시지 근거도 연결되어 있다.

동일한 최종 코드의 [인계 검토 대조](../evals/results/handoff/review-controls.json)는 **9/9**(오류 5개 거절·정상 4개 허용), [기존 검토 대조](../evals/results/handoff/regression-controls.json)는 **7/7**(오류 5개 거절·정상 2개 허용)이다. 이는 이미 준비한 초안을 검토하는 별도 검사로, 인계 생성 18회의 분모에 더하지 않는다.

자동 테스트 **82개**, JavaScript 문법 검사 **47개**를 통과했다. 인계/재문의 지침 분리, low 첫 생성과 medium 검토·수정, 원문 문맥 보존, 실패 시 편집 초안 보존, 미완료·불일치 평가 거절, 실패 시간·누락 사용량 및 짝지은 토큰 집계를 검증했다. UI는 변경하지 않았으며 브라우저 재시연·OCR·분석 정확도 재평가는 범위 밖이다.

## 채택하지 않은 첫 후보

[pilot](../evals/results/handoff/pilot.json)과 [나머지 실행](../evals/results/handoff/candidate-remainder.json)의 첫 후보는 저장 성공 18/18회, 중앙값 15.37초였다. 하지만 R03 두 번째 출력은 원래 없던 안내 날짜 질문을 추가했고, U06 두 번째 출력은 정정 없는 상충을 최종 안내처럼 표현했다. 저장 성공만 보고 채택하지 않았다. H03에도 계정 할인 적용 질문을 별도로 붙이는 경향이 있어 남은 질문을 평서문으로 전달하도록 보완했다. 기준 구현의 H04 출력은 원문 내 허위 작성 지시를 상충 안내로 요약했다.

따라서 생성 지침에 실제 정정과 미해결 모순을 구별하고 질문 확장을 피하도록 명시했다. 인계 검토에도 같은 기준을 추가했다. 첫 후보에서 얻은 오류 3개와 정상 출력 3개를 [검토 대조 자료](../evals/handoff-review-probes.json)로 고정한 뒤 검토 호출만 별도로 재평가했다. 이는 새 상담 생성 6건이 아니다.

[두 번째 후보](../evals/results/handoff/candidate-2.json)에서도 인계 18/18회를 저장했으나 H02의 '고객이 직접 확인', H03의 '고객님 계정'이 소비자가 보내는 글에 남았다. 내용 사실과 별도로 바로 보낼 수 있는 관점을 검사하도록 생성·검토 지침을 보완했다. 이 오류 2개와 원문 직접 인용의 고객 호칭을 허용해야 하는 정상 대조 1개를 더해, 최종 인계 검토 대조는 **오류 5개·정상 4개, 총 9개**다. 대조 정답은 각 검토 호출 전에 고정했다. 두 번째 후보의 수치를 최종 결과에 섞지 않았다.

[중간 검토 대조](../evals/results/handoff/intermediate-probes.json)는 6개 중 5개를 통과했다. H04에서 '허위 작성 지시가 있어 안내가 엇갈렸다'는 출력도 거절해야 하는데 허용했다. 이를 실제 상충 안내로 취급하면 안 된다는 예시를 검토 지침에 명시한 뒤 최종 비교와 9개 대조를 새로 실행했다. 실패한 대조를 삭제하거나 정답을 바꾸지 않았다.

관점 검토를 보강한 뒤 [기존 대조](../evals/results/handoff/intermediate-controls.json)에서 정상 인계의 '우리 집'을 '제 집'으로 바꾸라고 과도하게 거절한 경우도 발견했다(6/7 통과). 검토 범위를 자기 자신을 고객 호칭으로 서술한 오류에 한정하고 '우리/저희 집'·주어 생략·직접 인용은 허용하도록 명시했다. 그 직전에 시작한 비교는 두 결과만 저장된 상태에서 중단하여 [불완전 기록](../evals/results/handoff/interrupted-comparison.json)으로 보존했으며, 최종 집계에서 제외했다. 이후 동일한 최종 코드로 9개 인계 대조와 기존 7개 대조를 확인한 뒤 18쌍을 처음부터 다시 비교했다.

첫 후보의 기준 구현에서 NU06 한 번은 90초 시간 초과로 실패했다. [중간 비교](../evals/results/handoff/candidate-comparison.json)에 실패 대기 시간과 사용량 누락을 그대로 보존했고, 전체 토큰 절감률을 계산하지 않았다. 이를 제거하거나 최종 실행과 합치지 않는다. 공급자 변동이 있을 수 있으므로 최적화가 시간 초과 자체를 방지한다고 주장하지 않는다.

## 재실행

Node.js 24 이상에서 저장소 루트를 작업 디렉터리로 사용한다. 실제 유료 API를 호출하며 키는 환경변수 또는 숨겨진 stdin으로만 제공한다. 출력 파일은 덮어쓰지 않는다.

```powershell
node scripts/prepare-handoff-eval.mjs
node --env-file=.env scripts/evaluate-handoff.mjs --out .artifacts/eval/handoff-new.json
node scripts/compare-handoff.mjs .artifacts/eval/handoff-new.json
node --env-file=.env scripts/evaluate-handoff.mjs --only review-probes --out .artifacts/eval/handoff-review-new.json
node --test
node scripts/check.mjs
```

두 부분으로 실행한 기록은 비교 도구에 두 파일을 함께 전달한다. 구성이나 자료 해시가 다르면 합치지 않는다. 실패 호출의 사용량을 알 수 없으면 전체 토큰 절감률을 계산하지 않는다. `--key-stdin --interactive`는 키를 파일로 쓰지 않고 메모리에서 유지한다. 후속 JSON의 `only`로 케이스를 고르고 `only:"review-probes"`로 인계 검토 대조, `control:true`로 기존 초안 검토 대조를 실행할 수 있다. 종료는 `quit`이다.

이전의 58.09초는 다른 평가의 인계 3건 중앙값이므로 이 보고서의 18회 결과와 직접 절감률을 계산하지 않는다. 합성 자료·적은 반복 수·캐시 적중·공급자 및 네트워크 변동이라는 한계가 있다. 긴 실사용 상담 전체의 지연이나 일반 품질을 보증하지 않는다. 원문 확인과 사용자 편집 단계는 유지한다.

측정 설계는 [OpenAI 지연 최적화 가이드](https://developers.openai.com/api/docs/guides/latency-optimization)의 작업별 완료 시간과 토큰·수정 호출을 함께 확인하는 방식을 참고했다.
