# ReplyTrack 45초 초과 인계 후속 개선

평가일: 2026-11-14. 기준은 PR #8이 병합된 main `e7717f8a2dc14c4c4bc905f78c4d75cbf343016a`다. 이전 보고서와 평가 결과를 덮어쓰지 않는다.

## 원인과 변경

[이전 원본](../evals/results/handoff-tail/full.json)의 U06 개선안은 45.575초가 걸렸다. 첫 생성 7.289초가 '한 상담원/다른 상담원'을 추측했고, 서버 검증이 이를 차단한 뒤 medium 수정 17.395초와 medium 검토 20.891초를 실행했다. 실제 원문은 청구 유무가 다른 두 안내이며 서로 다른 담당자인지는 알 수 없다.

원문에 실제 담당자 언급이 없고 두 개 이상의 유효한 agent 출처가 있는 경우, 제한된 안내 전달 표현에서만 사람 구분을 정리한다. '한 상담원은/다른 상담원은' 뒤 직접 인용은 각각 서로 다른 원문에 존재해야 하며 '한 답변에서는/다른 답변에서는'으로 바꾼다. '한/다른 상담원에게는 …라고 안내받았다' 간접 전달도 답변 구분으로 바꾼다. '상담원들로부터 …인용… 안내를 받았다'는 복수 접미사만 제거한다. 인용·서술어·내용·출처를 그대로 두고 인원수와 시간 순서를 확정하지 않는다. 실제 담당자 언급·행동·요청·잘못된 출처와 허용하지 않은 표현은 일반 수정 경로를 따른다. 이후 서버 검증과 **동일한 medium AI 검토**를 거쳐야 저장한다. 특히 간접 인용·복수형의 내용 일치를 코드만으로 판정하지 않는다.

첫 생성 low, 의미 수정 medium, 모든 검토 medium을 유지했다. 생성·수정·의미 검토 및 분석·재문의 지침은 최종적으로 기준 구현과 런타임 문자열이 같다. 중간에 시도한 정정 정보 서술 지침 변경은 성능이 악화돼 제외했다. 모델 변경·검토 생략·출력 제한 축소·제품 요청의 임의 중단으로 시간을 줄이지 않았다. [ADR 0011](adr/0011-source-grounded-handoff-attribution.md)에 적용 조건을 기록했다.

## 방법

[최종 입력](../evals/handoff-attribution-final-cases.json)은 최종 API 호출 전에 고정했다. 전체 생성의 원문·분석 상태·ID·기준은 [첫 후보 자료](../evals/handoff-attribution-cases.json)와 같다. 기존 12개 분석 기록에서 U06 6회, NR05 3회, R03 2회, 나머지 각 1회로 전후 각 20회 전체 인계를 실행한다. 새로운 상담 20개나 분석 정확도 평가가 아니다. 별도 12쌍은 실패 초안 6개(실제 U06, 담당자·따옴표 변형, 중간 후보에서 관측한 복수형·간접 전달, 기존 R03·H02)를 두 번씩 재생한다. 최초 생성·실패 검토는 재생값으로 시간·토큰에 넣지 않는다. 서버가 거절한 U06 초안에 가짜 검토 실패를 재생하지 않으며 정리된 결과는 실제 AI 검토를 받는다.

양쪽 모두 `gpt-5-mini-2025-08-07`과 같은 원문·질문·약속·ID를 사용한다. 쌍마다 실행 순서를 번갈아 배치하고 작업자는 두 개다. 실패 시간도 포함하며 45초 초과는 엄격하게 `>45000ms`로 센다. 중앙값은 기존 도구의 가운데 두 관측값 중 큰 값, p95는 nearest-rank다. 20회의 p95는 두 번째로 큰 관측값이므로 최댓값도 제시한다. UI·OCR·분석 시간은 제외한다.

NR05 개선안의 첫 초안이 카드→계좌→카드 흐름을 '초기에 계좌'로 잘못 요약했고, 검토가 이를 거절해 50.520초가 걸렸다(첫 생성 5.443초, 검토 18.042초, 수정 14.251초, 재검토 12.782초). 이 실패 원인과 기록을 보존하고 정정 정보의 서술 지침을 바꾼 뒤 최종 비교를 처음부터 재실행했다. 중간 파일은 미완료이며 중단 시 진행 중이던 호출의 시간·사용량도 완전하지 않아 최종 성능 계산에 섞지 않는다.

정정 정보의 서술 지침까지 바꾼 [두 번째 후보 전체 비교](../evals/results/handoff-attribution/rejected-prompt.json)는 전후 각 20회 저장했지만 중앙값 14.984→16.398초, p95 19.823→30.278초, 총 토큰 84,554→96,440으로 악화됐다. NR05는 같은 순서 오류가 재발해 43.843초, U06은 복수형·간접 전달의 담당자 추정으로 3회 재작성이 필요했다. 이 후보를 채택하지 않고 생성 지침을 복원했으며 관측한 전달 표현도 제한적으로 정리하도록 보완했다. 수정 도중 시작된 [중간 재생](../evals/results/handoff-attribution/interim-repairs-partial.json)도 중단·보존했다. 최종 소스와 일치하지 않는 중간 수치는 최종 비교에 합치지 않는다.

## 재실행과 한계

```powershell
node scripts/prepare-handoff-attribution-eval.mjs
node --env-file=.env scripts/evaluate-handoff.mjs --suite attribution --out .artifacts/eval/attribution-new.json
node scripts/compare-handoff.mjs .artifacts/eval/attribution-new.json
node --env-file=.env scripts/evaluate-handoff.mjs --suite attribution --only repair-probes --out .artifacts/eval/attribution-repair-new.json
node scripts/compare-handoff.mjs .artifacts/eval/attribution-repair-new.json
node --test
node scripts/check.mjs
```

키는 환경변수나 숨겨진 stdin으로만 공급한다. 결과는 덮어쓰지 않으며 소스·입력·평가 코드 해시와 실제 모델·호출별 시간·사용량을 기록한다. 비교 도구는 서로 다른 전체 생성/실패 재생 측정의 혼합을 거절하고 사용량 누락이 있으면 전체 토큰 절감률을 계산하지 않는다.

반복한 합성 자료와 이를 보며 개선한 회귀 평가다. 개발 에이전트의 원문 대조이며 외부 사람의 독립 검수는 아니다. API·캐시·네트워크 변동을 통제한 대규모 실험이나 모든 인계의 45초 이내 완료 보장이 아니며 원문 확인·사용자 편집 단계를 유지한다.

참고: [OpenAI 지연 최적화 가이드](https://developers.openai.com/api/docs/guides/latency-optimization)의 불필요한 순차 호출을 줄이고 검증 후 결과를 표시하는 원칙을 적용했다.
