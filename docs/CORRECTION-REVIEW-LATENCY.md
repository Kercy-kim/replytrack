# 정정·의미 재검토 지연 개선

2026-11-16. 기준 main: `ea822f65745ee4b44c7931ec8b42270fef989c3a`.
모델은 전후 모두 `gpt-5-mini-2025-08-07`. 사용자 데이터 대신 가상 상담·독립 메모리 DB를 사용한다.

## 관측한 원인

이전 [등록·답변 측정](REGISTRATION-REPLY-LATENCY.md)의 R03 기한 철회는 단일 medium 요청이 36.445초였다. 응답 헤더 수신까지 36.440초, 본문 읽기는 약 3ms이며 추론 토큰은 2,496개였다. 25초에 보조 요청이 시작됐지만 원래 요청이 먼저 끝났다. 로컬 저장이나 화면 갱신이 긴 지연의 주원인은 아니었으며, 공급자 내부 대기·추론·네트워크 지연을 개별적으로 분리할 수는 없다.

영어 등록의 30.282초 사례는 첫 생성 약 17.723초 뒤, 불필요한 추가 자료 추정을 고치기 위해 전체 분석을 약 12.552초 다시 생성했다. 의심되는 질문 하나 외의 질문·제목·원문까지 재생성하는 직렬 작업이 있었다. 일반 심사 기간을 독립 약속으로 만든 경우에도 같은 전체 재생성이 적용됐다.

## 변경

- 기존 질문에 업체 답변만 추가된 짧은 일반 상담에서 조건이 없으면, 상태·이유·근거·약속 갱신에 집중한 지침을 사용한다. 이메일·조건부 답변·긴 대화의 첫 요청은 기존 전체 지침을 유지한다.
- 짧은 일반 상담의 단순 금액·사실 정정은 low를 사용할 수 있다. 기존 기한이 있는 약속의 정정·변경·철회·부정, 이메일 정정, 조건·긴 대화는 medium으로 처리한다.
- 인용·구조 검사를 통과한 뒤 의미 재검토가 필요하면 의심 질문만 다시 생성한다. 질문의 ID·고객 원문·제목을 제공하며 잘못된 초안의 상태·설명은 전달하지 않는다. 다른 질문은 보존하고 약속 전체·요약은 다시 판단한다.
- 일반 심사 기간에 대한 의심만 있으면 약속·요약 전용 출력과 지침을 사용한다. 실제 자료 수신 통보와 개별 처리 확약은 유지한다.
- 모든 원문은 계속 제공한다. 모델, 재검토의 medium 추론, 최대 재생성 1회, 인용·ID·완료·경계 검토와 취소·동시 수정 보호를 유지한다.
- 추가 대조 검사에서 발견한 경계도 보완했다. 이메일에서 일부 서류를 확인 중이라는 진행 설명과 확인 후 알려주겠다는 확약을 구분한다. 안내 시점 자체를 물었는데 기한을 받고도 low 결과가 waiting이면 원문을 medium으로 재검토한다. 코드가 상태를 자동 변경하지 않는다.

적용 경계는 [ADR 0026](adr/0026-focused-semantic-review.md)에 기록한다. 화면 기능을 추가하지 않았다.

## 측정 방법

`scripts/benchmark-review.mjs`는 `.artifacts/review-baseline-ea822f6`에 기준 커밋의 detached worktree를 준비한 뒤 실행한다. `--run --repeats=2 --out=새경로.json`으로 같은 입력을 버전별 2회, 작업자 2개로 실행하며 사례·반복별 전후 순서를 바꾼다. 최종 비교는 다른 실제 API 평가와 동시에 실행하지 않았다.

- 실제 새 답변: S06·R03·NS05·NU06. 같은 저장 상태와 원문에서 분석·검증·저장 전체를 측정한다. 버전별 8회이며 이메일 본문 읽기·브라우저 대기는 제외한다.
- 의미 재검토: REPAIR-DATE·DOCS·DURATION. 이전 실행에서 관측한 잘못된 첫 결과를 그대로 재생하고 그 뒤의 실제 API 수정·검증·저장을 측정한다. 버전별 6회다. **첫 생성 시간을 포함하지 않으므로 등록 전체 시간으로 해석하지 않는다.**
- 토큰은 실제 완료 요청의 확인된 사용량만 합산한다. 취소된 보조 요청의 사용량을 모르면 총비용 절감률을 제시하지 않는다.
- 소스 해시·정답·원문·호출 시간·사용량·판정 결과를 원본 JSON에 보존한다. 실패도 삭제하거나 성공 사례 통계로 바꾸지 않는다.

## 후보 실패와 적용 범위 축소

1. `candidate1.json`: 지침만 축소했다. 14/14 통과했으나 약속 재검토는 여전히 28초대가 나왔다.
2. `candidate2.json`: 범위 제한 재검토를 도입했다. 14/14 통과했지만 약속 전용 검토가 자료 수신을 누락하여 별도 완료 검토가 붙은 실행은 29.299초였다. 약속만 출력하는 스키마와 수신 통보를 보존하는 전용 지침을 추가했다.
3. `final-paired.json`: 당시 최종 후보라는 파일명이며 최종 채택 결과가 아니다. 13/14 통과, DOCS 재검토 1회 `AI_INCOMPLETE`가 발생했다. 이전 측정기의 오류 호출 시간·전송 정보 기록이 부족해 원인은 확정하지 못한다. 이후 측정기는 실패 호출도 시간·오류·전송 정보를 기록한다. 이를 품질 통과로 취급하지 않았다.
4. `routed-paired.json`: 짧은 기한 정정까지 low를 넓혔고 13/14 통과했다. NS05에서 같은 배송을 기한 없는 기존 약속과 새 날짜 약속 두 개로 중복 생성했다. 기한 있는 기존 약속의 정정은 medium으로 되돌렸다.
5. `selected-paired.json`: 이 파일도 중간 후보다. 13/14 통과, NS05의 명시적 날짜 변경을 충돌로 오해하고 약속을 두 개 생성해 경계 검토까지 39.801초 걸렸다. 정정으로 대체된 날짜는 미해소 충돌이 아니며 기존 약속 하나를 갱신한다는 지침을 보강했다.
6. `email20.json`은 짧은 지침을 이메일에도 넓힌 후보의 17/20 결과다. 향후 안내·발송 약속 누락과 알 수 없는 번호를 answered로 표시하는 실패가 있었다. 이메일의 첫 요청은 기존 전체 지침으로 되돌렸고 `email20-final.json`, `email20-progress.json`은 각각 20/20이었다.
7. 새 대조 사례에서는 실제 일부 서류 목록의 확인 중 설명을 미래 약속으로 확대하는 문제가 드러나 이메일 지침에 구분을 추가했다. 조건부 요금을 확정 답변으로 판단한 후보는 조건부 갱신에 기존 전체 지침을 유지하도록 축소했고, 영어 금액 정정을 충돌로 읽은 후보는 이메일 정정에 기존 medium을 유지하도록 되돌렸다. 중간 `corrections6*.json`의 실패를 보존한다.
8. CR01은 기한 취소를 부정해 같은 약속·기한을 재확인한 대조다. 첫 채점이 약속의 마지막 메시지 인용만 허용해, 같은 기한의 원래 약속을 인용한 정상 결과를 실패로 표시했다. 이 사례만 동등한 두 약속 원문을 허용했다. 질문에는 최신 답변 근거를 요구하고, 상태·기한·ID 기준은 유지했다. 그 밖의 원문·상태 정답을 통과에 맞춰 변경하지 않았다.
9. `timing4.json`의 T02는 low 첫 분석이 안내 시점 질문을 waiting으로 남겨 3/4였다. 위의 시간 대상 재검토를 추가한 `timing4-verified.json`은 4/4 통과했다. 첫 생성 요청 자체를 더 큰 모델이나 더 높은 추론으로 바꾸지 않았다.
10. 기존 48건 첫 실행 `full48.json`은 48/48, 반복 실행 `full48-verified.json`은 47/48이었다. NS03에서 확인 완료 통보에 `deadlineCleared=true`를 넣어 기존 내일 기한을 지웠다. 철회 단서 없는 삭제를 약속 전용 medium 검토로 돌리고 재검토에도 같은 문제가 있으면 저장하지 않도록 했다. 관측 오판을 그대로 재생한 실제 복구 2회는 모두 통과했다(`deadline-repair.json`). 새 보호 검사를 이전 모든 원본 호출에 적용하니 NS03과 기한이 원래 비어 있던 S06만 영향을 받았다. 나머지 46건은 기존 결과를 유지하고 이 두 사례는 별도로 처음부터 재평가해 모두 통과했다.
11. 실제 누락 복구 대조를 반복한 한 실행은 두 번째 출력의 인용·상태 검사에서 `AI_EVIDENCE`로 중단됐다. 당시 스크립트가 예외 전에 결과를 저장하지 않아 어떤 참조가 실패했는지는 확정할 수 없다(`scope-controls-aborted.json`). 검사 실패는 저장 전에 차단됐다. 사례별 성공·실패·원본을 즉시 저장하도록 측정기를 보완했으며 `scope-controls-final.json`의 두 대조는 통과했다. 실패를 없었던 것으로 집계하지 않는다.

## 실제 웹 확인

실제 Chrome과 OpenAI API로 환불·영어 계정 복구의 등록, 새 답변 전후 비교와 진행 요약, 재문의 생성·검토·편집·저장·복사·재접속을 확인했다. [웹 기록](../evals/results/review-latency/browser-verified.json)은 마지막 기한 삭제 보호 추가 직전 실행이며, 추가 후에는 전체 로컬 브라우저 회귀와 영향 사례의 실제 API 재평가를 수행했다. UI 코드는 변경하지 않았다.

| 동작 | 환불 문의 | 영어 계정 복구 |
| --- | ---: | ---: |
| 등록·분석 — 본문 읽기·화면 대기 포함 | 17.293초 | 28.677초 |
| 새 답변 반영·비교 | 10.312초 | 16.733초 |

각 한 번의 기능 검증이며 동시 품질 평가가 있었으므로 성능 전후 비교에 사용하지 않는다. 영어 답변은 필요한 자료·심사 기간을 answered, 사례 번호를 unanswered로 유지했고, 거래 ID 수신 통보 한 개만 reported이며 실제 복구 완료로 바꾸지 않았다. 영어 재문의는 사례 번호만 요청했다.

환불 재문의는 생성·검토·수정을 거쳐 저장됐으나, 직접 읽었을 때 이미 안내된 안내 시점을 다시 묻는 부연이 남았다. 초기 질문 제목의 범위가 넓어진 영향이며 이번 분석 지연 최적화로 바뀌는 초기 일반 요청은 아니다. 재문의 기능 검사 통과가 문장 품질의 완전성을 뜻하지 않는다. 이번에는 초안 생성 로직까지 변경하지 않았다.

## 검증 해석

고정 가상 자료의 자동 기준과 개발 에이전트의 원문 대조이며 외부 사람 평가나 실제 사용자 전체의 정확도는 아니다. `initial-contract.json`은 이메일 품질 보완 전의 기록이다. 최종 오프라인 첫 요청 비교 `initial-contract-final.json`에서는 일반 상담 5개가 기준 main과 같고, 이메일 1개는 진행 설명·미래 확약 구분 지침만 달라졌다. 스키마·입력·추론량은 같다. 이는 첫 요청 비교이며 후속 재검토가 같다는 의미는 아니다.

재검토는 모든 의미 오류를 식별하거나 없애는 보장이 아니며, 공급자 변동과 추가 검토 때문에 30초 이상 걸릴 가능성은 남는다.
