# ReplyTrack 가상 상담 20건 실제 AI 평가

평가일: 2026-11-14. Windows / Node.js 24.22.1. 실제 응답 모델: `gpt-5-mini-2025-08-07`.

## 결과 요약

배송 7건·환불 7건·구독 6건을 실제 OpenAI API로 평가했다. 질문 상태의 사전 기준 일치는 **27/31 → 29/31(93.5%)**, 상담 단위 전체 분석 기준 통과는 **14/20 → 18/20**으로 개선됐다. 마지막 20건 전체 평가에서 미해결을 `answered`로 잘못 표시한 경우는 **0/15**였다. 중간 수정에서는 이 오류가 2건 발생했고, 이를 고쳐 재검증한 기록도 보존했다.

31회는 **서로 다른 질문 27개 + 후속 답변에 따른 재판정 4회**다. 독립된 31개 상담이 아니다. 정답은 첫 API 호출 전에 개발 에이전트가 작성했으며 외부 사람이 검수하지 않았다. 동일한 데이터를 보며 수정한 회귀 평가이므로 이 수치를 실제 서비스 전체의 정확도로 일반화할 수 없다.

## 범위와 재현 자료

- 입력: [고정한 가상 상담과 기대값](../evals/support-cases.mjs). 실제 고객 자료 없음.
- 데이터 SHA-256: `ab86201457d670ffd62d4844fa66e72711bb4be91ea677260946b3c98a904b8d`.
- 분석: 초기 20회 + 새 답변 반영 3회(S06, R03, U04).
- 초안: 재문의 4건 + 인계 3건. 생성·제품 내부 검토와 별도로 개발 에이전트가 출력 전체를 원문과 대조했다. 외부 사람의 평가 또는 블라인드 평가는 아니다.
- 실행: 실제 `ReplyTrack` 서비스와 메모리 SQLite, 실제 Responses API. 사용자 DB와 예제 모드는 사용하지 않았다.
- [실행 방법과 채점 규칙](../evals/README.md), [평가 스크립트](../scripts/evaluate-ai.mjs), [자동 채점기](../evals/grade.mjs).

정답 파일을 결과에 맞춰 수정하지 않았다. 아래 최종 분석 지표는 마지막 **20건 전체 실행**을 기준으로 하며, 이후 초안 검증만 보완한 뒤 7개 초안 대상 사례를 별도로 재실행했다. 두 실행의 유리한 분석 결과를 골라 합치지 않았다.

## 발견한 문제와 수정

1. **초안 화자 혼동·질문 누락:** 소비자가 보낼 글인데 상담원처럼 개인정보를 요구하거나 대신 안내하겠다고 작성했다. 소비자 관점을 명시하고 선택 질문 전체 포함을 요구했다. 생성 뒤 별도 의미 검토와 최대 한 번의 수정 과정을 추가했다.
2. **기한 철회 누락:** `dueText`가 비면 이전 날짜를 무조건 복구했다. `deadlineCleared`와 검증된 후속 원문으로 철회를 구분해 현재 기한을 비우고 전후 비교에 기록한다. 단순 완료 통보는 이전 기한을 보존한다.
3. **정책과 약속 혼동:** 조건별 반품비 부담 안내를 실제 개별 처리 약속으로 만들었다. 질문의 정보 답변과 개별 수행 행동을 구별하도록 수정했다.
4. **정보의 대상과 정정 처리:** 실제 처리 날짜와 ‘그 날짜를 알려줄 날’을 혼동하거나 명시적 정정을 계속 모순으로 취급했다. 질문의 대상·제공된 정보·최신 정정을 먼저 판단하도록 했다.
5. **근거 없는 답변 대기:** 향후 안내 약속 없이 미정이라는 이유만으로 대기로 분류했다. 서버에서 같은 질문·근거 메시지에 연결된 향후 약속이 없으면 AI 판정을 확인 필요로 낮춘다. 사용자 수동 상태는 보존한다.
6. **담당자 신원 추정과 검토 AI의 실수:** 메시지 역할만 보고 “같은/다른 상담원”을 단정했다. 검토 AI가 이 오류를 통과시키기도 해, 원문에 없는 담당자 구분 표현을 서버가 추가 차단한다. 의미 검토의 reasoning effort만 `medium`으로 높였다.
7. **초안 본문에 내부 참조 ID 노출:** 메시지 UUID를 본문 괄호에 적는 경우가 있었다. 기존 숫자 검증이 저장은 막았지만 원인을 정확히 설명하지 못해 수정이 실패했다. 본문과 근거 ID 필드를 명확히 분리하고 `DRAFT_REFERENCE`로 구체적인 수정 피드백을 제공한다. 원문에 실제로 있는 고객 접수번호 등은 허용한다.

설계와 제한: [기한 철회·답변 대기 검증](adr/0004-explicit-deadline-retraction.md), [초안 검토·수정 상한](adr/0005-bounded-draft-review.md).

## 초안과 검토기 검증

최초 초안 7건 모두 소비자 관점에 어긋나는 표현이 있었다. 그중 S06은 원문에 있던 과거 금액을 적으면서 해당 메시지 ID를 근거에 넣지 않아 서버가 저장을 거절했다. 이는 없는 금액을 새로 만든 오류와는 구별한다.

실패 출력으로 검토기 자체도 검사했다. 낮은 추론 강도의 검토는 질문 누락과 담당자 추정은 잡았지만 상담원 관점의 초안을 통과시켜 **2/3**이었다. 최종 검토 구성은 같은 실패 출력 3개를 모두 거절해 **3/3**이었다. 이 부정 사례는 새 상담이나 새 초안 생성으로 세지 않는다. 제품 검토기의 통과만으로 품질 성공을 선언하지 않고 아래 최종 초안을 별도로 대조한다.

최종 초안 대상 7건 재실행은 **6건 저장 성공, 1건(R02) 서버 차단**이었다. R02는 본문 UUID에 대한 구체적 검증·피드백을 추가한 뒤 별도로 재실행해 정상 생성됐다. 따라서 아래는 **6건 + 수정 후 재검증 1건**이며 단일 실행 7/7 성공으로 보고하지 않는다. 새 검증 규칙은 기존 6개 성공 출력에도 적용해 모두 통과하는지 확인했다.

| 사례 | 최종 원문 대조 | 확인한 내용 |
| --- | --- | --- |
| S02 재문의 | 통과 | 도착일과 배송비 두 질문 모두 포함, 운송장 재요청 없음 |
| S04 재문의 | 통과 | 요금표를 실제 적용 금액으로 단정하지 않고 주문별 금액 확인 요청 |
| S06 인계 | 통과 | 배송비 정정과 운송 중 안내 반영, 사용자 수령 완료로 단정하지 않음 |
| R02 재문의 | 재검증 통과 | 최종 환불액 문의, 내부 UUID 제거, 추가 차감 여부는 질문으로 표현 |

| U06 인계 | 통과 | 서로 다른 답변의 충돌을 설명하되 서로 다른 사람이라고 추정하지 않음 |

마지막 전체 실행은 138.6초였으며 API **호출 한 번당** 지연 중앙값 6.63초, p95 11.33초였다. 초안은 여러 호출이므로 이 시간을 초안 하나의 대기 시간으로 해석하면 안 된다. 현재 제품은 분석·생성 `low`, 초안 의미 검토만 `medium`이며 초안 한 건에 보통 2회, 수정 시 최대 4회 호출한다. 가격을 추정하는 대신 실제 토큰 사용량을 기록했다.

최종 초안 7건 대상 재실행은 24회 호출, 입력 33,630 / 출력 14,079토큰이었다. R02 수정 후 추가 실행은 분석 포함 3회 호출, 입력 3,582 / 출력 1,556토큰이다. 성공한 최종 초안 요청 7개의 생성·검토 합산 대기는 중앙값 **15.46초**, 범위 **11.24~24.02초**였다. R02가 차단되기까지 걸린 14.72초는 별도이며, 그 뒤 재검증 초안 생성에 12.26초가 추가됐다.

전체 작업은 중간 실행과 부정 사례까지 합쳐 **192 API 호출**, 입력 **259,181** / 출력 **120,689토큰**이었다. 20건을 한 번 처리하는 데 필요한 비용과 혼동하면 안 된다. 의미 검토를 추가하면서 호출 수와 지연이 늘었으며, 비용 절감 효과를 측정한 실험은 아니다.
