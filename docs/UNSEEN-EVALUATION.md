# 기존에 사용하지 않은 상담 20건 평가

평가일: 2026-11-14. 실제 모델: `gpt-5-mini-2025-08-07`.

## 최초 평가와 수정 후 평가를 구분

기존 28건과 원문을 재사용하지 않은 **배송 7·환불 7·구독 6건**을 새로 작성했다. 첫 API 호출 전에 질문·상태·답변 근거·약속·기한의 기대값을 고정했으며, 결과를 보고 정답을 바꾸지 않았다. 최초 실행에는 당시 main의 제품 코드와 프롬프트를 그대로 사용했다. 입력은 가상 자료이며 실제 고객 데이터가 아니다.

**처음 보는 자료에 대한 최초 분석 통과는 17/20건이었다.** 질문 상태는 모두 맞았지만 처리 약속의 추가·누락과 변경 기한에서 실패했다. 그 결과로 수정한 뒤 동일한 20건 전체 분석은 **20/20건**을 통과했다. 후자는 독립 성능이 아닌 회귀 결과다.

| 지표 | 최초 실행 | 수정 후 전체 분석 |
| --- | ---: | ---: |
| 상담 단위 분석 기준 전체 통과 | 17/20 | 20/20 |
| 분석 단계(후속 답변 포함) | 21/24 | 24/24 |
| 질문 추출·상태 일치 | 32/32 | 32/32 |
| 기대 답변 메시지 인용 | 32/32 | 32/32 |
| 기대 약속 상태·기한 | 6/8 | 8/8 |
| 미해결을 답변 받음으로 오판 | 0/15 | 0/15 |
| 실제 원문에 존재하는 인용 | 73/73 | 72/72 |

32회는 20개의 독립 상담 수가 아니라 질문별 판정과 후속 재판정의 합계다. 약속 통과율은 기대한 약속의 일치 수이며, **불필요한 추가 약속도 상담 전체 통과에서는 실패**로 처리한다. 인용 개수는 답변마다 달라질 수 있으므로 원문 일치율과 질문별 필수 근거를 함께 본다.

분석 결과와 초안 결과는 별도 지표다. 최초 초안 6건은 제품 검토를 통과했지만, 개발 에이전트가 원문을 대조한 결과 NR05의 안내 순서 오류로 **5/6건**이었다. 이후 담당자 수 추정, 근거 없는 비용 차감 전제, 검토 지시가 새 질문을 만드는 문제까지 보완했다. 전체 20건 집계의 초안은 **6/6건 생성·검토·원문 대조 통과**다. 외부 사람의 검수나 문장 자연스러움 점수는 아니다.

원본: [최초 실행](../evals/results/unseen/baseline.json), [수정 후 20건 집계](../evals/results/unseen/final.json). 집계는 같은 소스 해시로 실행한 서로 겹치지 않는 [초안 포함 6건](../evals/results/unseen/final-drafts.json)과 [나머지 14건](../evals/results/unseen/final-rest.json)을 합친 것이다. 사전에 정한 초안 유무로 나눴으며 각 실행의 모든 결과를 포함한다. 하나의 연속 실행으로 가장하지 않으며 원본 파일 해시와 케이스 목록을 집계에 보존했다. 원본의 `semanticReview`는 실행 당시 자동 기록한 검수 대기 표시이며, 개발 에이전트의 대조 결과는 이 보고서에 따로 적는다.

## 발견한 문제와 수정

1. **단순 안내와 업무 수행 혼동:** 현재 번호를 알려주는 답변을 완료 약속으로 만들지 않는다. 반대로 개별 승인·해제·확인 완료는 사전 약속이 없어도 `reported`로 추출한다.
2. **새 기한을 삭제:** 새 날짜로 변경한 경우와 대체 기한 없이 철회한 경우를 구분한다. 새 날짜는 기존 약속 ID에 반영하고 비교 이력을 유지한다.
3. **중간 단계·정보 미정의 오판:** 처리의 중간 단계는 부분 정보다. 결과 미등록을 통과·불통과가 확정된 답변으로 바꾸지 않는다.
4. **원문 ID·인용문 복사 오류:** ID를 대화·역할별 enum으로 제한한다. 저장 전에 정확한 인용을 검증하고, 틀린 경우에만 한 번 수정 요청한다. 재검증 실패·API 장애·동시 수정 시 이전 기록과 추가 원문을 보존한다. 분석 시도 횟수와 합산 사용량을 저장한다.
5. **초안의 안내 순서·담당자 추정:** 최초·중간·최종 안내를 구분하고 담당자 수를 추측하지 않는다. `상담원들` 같은 복수 표현도 원문 근거가 없으면 거절한다. 반면 단순 역할명 ‘상담원’ 자체는 동일인 주장으로 오인하지 않는다.
6. **추정 설명이 초안의 사실로 전파:** AI의 판단 이유와 추천 `followUp`을 초안 생성·검토 입력에서 제외했다. 질문과 검증된 인용, 실제 원문으로 판단하며 근거 없는 차감 관계를 가져오지 않는다.
7. **부분 답변과 확인 필요의 흔들림:** 근거가 있는 `review` 질문만 별도 검토해 `partial/review`를 선택한다. 답변 받음으로 올리거나 근거·약속을 바꿀 수 없다. 알 수 없는 ID·중복·다른 상태가 나오면 저장하지 않는다.
8. **미답변과 근거의 모순:** `unanswered`인데 evidence가 있으면 한 번 수정 요청한다. 관련성이 있는 안내라면 상태를, 무관한 안내라면 근거를 고치게 한다. 서버가 근거를 일괄 삭제하거나 정답 상태를 강제하지 않는다. 인용 수정과 같은 1회 한도를 사용한다.
9. **초안 수정 제안이 질문 범위를 확대:** 검토 AI가 잘못된 차감 전제를 지우는 대신 차감 여부를 새로 물으라고 제안한 사례를 보완했다. 수정 제안도 사용자 요청으로 취급하지 않으며 선택 질문만 남긴다. 질문 하나에는 짧은 한 문장을 허용하고 불필요한 최소 분량 요구를 제거했다.
10. **질문 ID를 초안 출처로 혼동:** 초안 수정 후 새 6건을 다시 실행하면서 실제 메시지 ID에 질문 ID까지 섞는 오류가 나왔다. 분석뿐 아니라 초안의 출처 목록도 해당 상담의 실제 메시지 ID enum으로 제한했다. 서버 검증과 실패 시 이전 초안 보존도 유지한다.
11. **확인 미기록을 미확인 사실로 단정·내부 날짜 노출:** 인계문에서 직접 확인 여부가 없는데 확인하지 않았다고 단정했고, 수정 과정에서 내부 UTC 시각을 본문에 넣었다. 초안에는 발화자·원문·메시지 ID와 약속의 원문 기한을 전달하고 내부 시간값·계산된 날짜는 제외한다. 사용자가 직접 확인한 기록은 `confirmedByUser=true`로 보존하며 미기록을 false 사실로 전달하지 않는다. 생성 지침도 확인/미확인을 모두 추측하지 않도록 명시했다.

모델은 변경하지 않았다. 최종 구성은 분석·모든 초안 생성·검토에 reasoning effort `medium`을 사용한다. 분석은 기본 1회, 인용·상태 일관성 수정 1회와 경계 검토 1회를 포함해 최대 3회다. 초안은 생성·검토와 1회 수정을 포함해 최대 4회다. [ADR 0007](adr/0007-information-actions-and-rescheduling.md)에 의미 기준, 입력 분리와 비용 선택을 기록했다. 서버가 평가 ID나 특정 단어를 보고 정답 상태를 강제하는 방식은 사용하지 않는다.

## 기존 자료 회귀와 마지막 수정의 범위

- [기존 28건 회귀](../evals/results/unseen/regression-1.json)는 분석 **27/28건**, 상태 38/39회였다. U03의 일부 기간 요금을 확인 필요로 판정했고, R02 초안은 반품비 차감을 전제했다.
- [관련 6건 재평가](../evals/results/unseen/regression-2.json)는 **5/6건**으로 U03이 계속 흔들렸고, AI가 만든 추천 질문이 초안에 전달되는 문제를 확인했다.
- 입력 분리·경계 검토 후 [2건 재평가](../evals/results/unseen/regression-3.json)에서 U03은 통과했다. 이 실행의 U03은 최초 분석부터 partial로 나와 경계 검토가 고쳤다고 주장하지 않는다. R02는 미답변에 다른 질문의 근거를 붙인 모순으로 실패했다.
- 일관성 검사 후 [R02 실행](../evals/results/unseen/r02-final.json)은 분석을 통과했지만 초안 수정 지시가 질문 범위를 넓혀 최종 저장에 실패했다. 오류 초안은 저장하지 않았으며 실패 원본도 보존했다.
- 질문 범위 보완 후 [R02·U03 실행](../evals/results/unseen/scope-regression.json)은 **2/2건**, 상태 **3/3회**와 R02 초안을 통과했다. R02는 ‘최종 환불액은 얼마인가요? 안내 부탁드립니다.’로 원래 질문만 요청했다. 이번 U03은 최초 review를 경계 검토가 partial로 바로잡았다.
- 같은 지침으로 [새 초안 사례 6건](../evals/results/unseen/scope-drafts.json)을 재실행했을 때 분석은 6/6건이었지만 NS03·NR02의 초안이 질문 ID를 출처에 섞어 저장에 실패했다. 이 결과로 출처 ID 스키마를 추가했다.
- 출처 제한 후 [6건 재평가](../evals/results/unseen/reference-final.json)의 분석은 **6/6건**, 초안 저장은 **5/6건**이었다. 재문의 3건의 질문 범위·원문 근거는 모두 맞았고 ID 혼동도 없어졌다. NS03 인계는 확인 여부 단정이 검토에서 거절된 뒤 내부 UTC 시각을 넣어 서버 검증에 실패했다. 이 실행도 성공으로 덮어쓰지 않았다.
- 초안 입력의 날짜·확인 미정 정보 분리 후 [인계 3건 재평가](../evals/results/unseen/handoffs-final.json)는 분석 **3/3건**(후속 포함 6단계), 상태 **6/6회**, 약속·기한 **4/4회**, 초안 **3/3건**을 통과했다. 모두 첫 생성·검토로 저장됐고 원문 대조에서도 순서·철회·확인 여부 추정 오류가 없었다. 직전 실행의 재문의 3건과 이 실행의 인계 3건을 구분하며, 마지막 코드로 초안 6건을 한 실행에서 통과했다고 주장하지 않는다.
