# ADR 0014: 질문 범위에 맞춘 짧은 판정 이유

- 상태: 채택
- 날짜: 2026-11-14

## 문제

ADR 0013 이후 전체 회귀에서 질문 상태는 맞았지만, 자동 갱신 방법에 묻지 않은 앱/웹 경로를 덧붙이고 실제 입금 여부에 입금 시점을 추가하는 설명이 남았다. 분석 스키마가 모든 상태에 제공된 정보와 빠진 정보를 각각 설명하도록 요구해, 프롬프트의 질문 범위 제한과 충돌했다. 부분 답변에는 질문과 인용을 반복하며 분류 과정을 설명하는 문장도 있었다.

## 결정

분석과 partial/review 경계 검토에 같은 reason 스키마 설명을 적용한다. 분석 출력은 상태를 먼저 정하고 이유를 작성한다. 답변 받음은 받은 답만, 부분 답변은 받은 부분과 질문한 대상에서 남은 부분만, 답변 대기는 향후 안내 약속만, 확인 필요는 미정·식별 불가·상충 사유만 설명한다. 미답변의 서버 고정 문구는 유지한다.

이유는 보통 30~70자 정도의 한 문장을 목표로 하되, 숫자·조건·부정·정정·상충을 길이 때문에 삭제하지 않는다. 원문 인용은 별도 evidence에서 보여 주므로 이유에서 문장 전체를 반복하지 않는다. 업체가 안내한 완료를 앱이 직접 처리하거나 확인한 것처럼 쓰지 않는다. 실제로 질문한 상세 경로나 시각의 미정은 남긴다.

짧게 쓰는 범위는 reason이며 evidence가 아니다. 부분 안내와 미정 설명이 함께 있으면 둘 다 인용한다. 초기 상태가 review여도 후속 경계 검토에서 partial로 판정할 유용한 안내를 근거에서 빠뜨리지 않도록 분석 지침을 명시했다.

반복 회귀에서 방법을 알려준 현재 예약 상태 질문이 answered로 바뀐 사례가 있어, 예약 가능성·적용 시점 안내와 실제 계정의 예약 완료를 구별하는 예시를 보강했다. 이는 ADR 0006의 기존 partial 기준을 명확히 한 것이다. 같은 상태 질문의 재문의에 새 조작·예약·확인 절차를 덧붙인 사례도 있어, 생성과 검토에서 현재 상태만 요청하도록 명시했다. 실제 방법을 질문한 경우의 안내는 계속 허용한다.

ADR 0006의 상태 기준, ADR 0013의 인계 질문 범위와 이전 약속 보존은 바꾸지 않는다. 필드·자료형·모델·추론 설정·호출 상한도 유지한다. 추가 생성 호출, 문자열 잘라내기나 문장 정규식 보정은 도입하지 않는다.

## 검증

기존 배송·환불·구독 48건의 원문과 기대값을 그대로 사용한다. 별도 4건은 상세 경로·입금 시각·환불 예외 조건·배송 날짜와 시각을 대조한다. `evals/reason-quality.mjs`는 알려진 불필요한 표현과 필요한 사실의 누락을 검사하는 평가 보조 도구이며 제품 응답에는 적용하지 않는다. 자동 검사와 모든 저장 이유·초안의 원문 대조를 구분한다. 결과와 중간 실행은 [판정 이유 평가 보고서](../REASON-SCOPE-EVALUATION.md)에 기록한다.

## 한계

길이 목표는 강제 제한이 아니며 생성 변동이 있다. 고정 합성 상담의 회귀와 표현 대조로 실사용 전체의 정확도를 보증하지 않는다. 정규식 검사는 의미 평가를 대체하지 않는다.
