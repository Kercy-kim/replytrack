# ADR 0007 — 정보 안내, 업무 수행, 기한 변경의 구분

- 상태: 채택
- 날짜: 2026-11-14
- 근거: 기존 평가에 사용하지 않은 상담 20건의 최초 실행

## 문제

질문 상태는 맞더라도 단순 운송장 안내를 별도의 완료 통보로 만들거나, 명시적인 환불 승인 완료를 처리 약속에서 누락했다. 또한 방문 날짜를 새 날짜로 변경했는데 기한 철회로 해석하여 날짜가 사라졌다. 인계 초안에서는 중간에 나온 안내를 최초 안내라고 표현했다.

## 결정

- 번호·금액·장소를 알려 주는 현재 답변 자체는 처리 약속이 아니다. 개별 건에서 승인·접수·해제·확인 등을 실제 수행했다고 명시한 경우는 `reported`다. 사전 약속이 없거나 질문 상태가 답변 받음이어도 추출한다. 사용자 확인 완료로 바꾸지는 않는다.
- 이미 약속한 확인·안내를 이행했다면 기존 약속을 `reported`로 갱신한다. 같은 행동을 중복 생성하지 않는다.
- 기한을 새 날짜로 바꾸면 같은 약속 ID에 새 `dueText`를 적용하고 `deadlineCleared=false`로 둔다. 이전 날짜를 취소했다는 말이 함께 있어도 새 기한이 있으면 철회 플래그를 사용하지 않는다.
- 대체 기한 없이 이전 기한을 명시적으로 철회한 경우에만 `deadlineCleared=true`다. 진행·완료 통보에서 기한을 단순 생략하면 이전 기한을 유지한다. ADR 0004의 원문 검증과 변경 이력 보존은 유지한다.
- 초안의 처음·초기·최종 표현은 전체 원문의 메시지 순서와 일치해야 한다. 중간 안내를 최초 안내로 바꿔 요약하지 않는다. 정정 이력을 짧게 쓸 때는 ‘안내가 엇갈렸으나 최종적으로 정정받았다’처럼 정확하게 압축한다. 생성과 검토 프롬프트 모두 같은 기준을 적용한다.

이는 기존 상태·저장 형식을 바꾸지 않는 의미 판정의 보완이다. 특정 평가 ID나 단어로 출력을 강제하지 않는다. 새로운 자료의 최초 실행과 수정 후 재실행을 분리하고 정답을 그대로 유지한다. 수정에 사용한 이후의 결과는 미사용 자료에 대한 독립 성능이 아닌 회귀 결과로 보고한다.

## 재평가에서 확인한 추가 보완

- 여부 질문의 ‘미등록/조회 불가’는 부정 결론이 아니라 정보 미정이다. 중간 진행 정보만 제공하면 부분 답변이며, 통과/불통과가 확정됐다고 바꾸지 않는다.
- 모델은 계속 `gpt-5-mini`를 사용하되 분석과 인계 생성의 reasoning effort를 `medium`으로 올린다. 회귀 평가에서 재문의가 비용 차감 관계를 전제한 문제도 확인되어 재문의 생성까지 `medium`으로 높였다. 의미 검토는 기존 `medium`을 유지한다. 추론 설정 변경 자체는 호출을 추가하지 않으며 초안의 1회 수정 한도를 유지한다. 분석 인용 오류의 별도 수정 한도는 아래에 명시한다. 이는 토큰·시간 증가를 감수한 품질 선택이며 개선에 기여한 요인을 각각 분리해 실험한 것은 아니다.
- 분석 스키마를 요청마다 복사하여 고객 질문의 source ID는 실제 customer 메시지, 답변·약속 ID는 실제 agent 메시지의 enum으로 제한한다. 해당 역할의 메시지가 없으면 관련 배열의 `maxItems=0`으로 둔다. 대화 사이에 스키마를 공유·수정하지 않으며 기존 ID와 저장 구조는 유지한다. 원문 인용 및 역할의 서버 검증도 그대로 유지한다. 구조 제약은 의미 정확성을 보증하지 않는다.
- 검토 AI는 ‘상담원’이라는 역할명 사용만으로 동일인 추정이라고 거절하지 않는다. 이름, A/B, 같은/다른 사람, 인원수처럼 실제 식별 주장이 있을 때만 원문과 대조한다. 기존 잘못된 초안 5개와 정상 초안 2개로 거절·허용 양쪽을 확인한다.
- 같은 처리 건의 입고·접수 등 중간 진행 단계는 결과가 미등록이어도 실질적인 부분 정보로 본다. 따로 질문한 다른 항목의 답을 자동으로 옮겨 쓰지는 않는다.
- ID를 제한해도 모델이 인용문의 단어를 바꿔 쓸 수 있다. 실제 분석은 저장 전에 source·evidence의 ID, 역할, 정확한 부분 문자열을 모두 검사한다. 불일치할 때만 오류 경로와 이전 출력을 전달하여 한 번 수정 요청한다. 두 번째에도 불일치하면 `AI_EVIDENCE`로 실패하고 이전 분석·사용자 수정·추가 원문을 보존한다. API 장애 자체는 재시도하지 않으며 두 번째 요청 전에도 버전을 확인한다. 수정한 출력은 다시 같은 검사를 거친다. 의미 분류를 서버가 단어 규칙으로 고치지는 않는다.
- 미답변(`unanswered`)인데 답변 근거가 붙은 출력도 저장 전 오류로 판단한다. 단순히 근거를 지우거나 상태를 강제하지 않고 모델이 관련성을 다시 판단해 근거 또는 상태를 수정하게 한다. 인용 수정과 같은 한 번의 수정 기회를 사용한다.
- 기본 분석은 1회, 인용·상태 일관성 수정까지는 최대 2회 호출한다. 아래 경계 검토를 포함한 최종 한도는 3회다. 저장된 분석 메타데이터에 시도 횟수와 모든 호출의 합산 사용량을 남긴다. 초안은 기존 생성·검토 및 1회 수정 한도를 유지한다.

스키마 제약은 [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)의 enum 및 배열 제약을 사용한다. API 오류·불완전 출력은 기존 오류 처리 경로를 유지한다.

## 반복 실패에서 확인한 입력 분리와 경계 검토

기존 자료 재평가에서도 일부 기간의 요금을 받은 질문이 확인 필요로 흔들렸다. 또한 AI가 만든 `followUp`에 비용 차감 전제가 들어갔고, 초안 생성·검토가 이를 사용자 요구처럼 받아들였다. 프롬프트만 반복해서 늘리는 대신 다음과 같이 입력과 검토 단계를 분리한다.

- 초안 생성·검토에는 질문의 ID·제목·원문 source·현재 상태·검증된 evidence만 전달한다. AI의 `reason`, `aiReason`, 추천 `followUp`은 전달하지 않는다. 실제 원문 메시지는 모두 제공한다. 평가용 대조 검사도 같은 입력 함수를 사용한다.
- 유효한 답변 근거가 있는 `review` 질문에만 짧은 경계 검토를 한 번 적용한다. 원문과 최소 질문 정보로 `partial` 또는 `review`만 선택하며, 답변 받음·사용자 확인 완료로 승격할 수 없다. 중간 진행 단계·방법·같은 청구 항목의 다른 기간 정보가 있는지와 해결되지 않은 충돌을 구분한다.
- 검토는 지정한 질문 ID를 정확히 한 번씩 반환해야 한다. 알 수 없는 ID, 중복, 다른 상태, 형식 오류나 공급자 장애가 있으면 저장하지 않는다. 질문·근거·약속은 수정하지 않으며 사용자의 수동 상태는 기존 규칙대로 유지한다. 원래 AI 출력은 평가 로그에 그대로 남긴다.
- 분석 메타데이터에는 경계 검토 모델·질문 수와 전체 호출의 합산 토큰을 기록한다. 분석은 통상 1회, 인용 수정 1회 및 경계 검토 1회를 포함하면 최대 3회다. 경계 검토도 같은 모델의 판단이므로 정답 보장은 아니다.

물품의 이동 현황만으로 업체가 특정 업무를 수행했다고 추정하지 않는다. 도착·운송 중이라는 현황은 질문의 부분 정보로 활용할 수 있지만, 명시적인 접수 처리·확인 완료나 기존 약속의 이행이 없으면 별도의 처리 약속을 만들지 않는다.

초안 수정 피드백도 AI가 생성한 제안이므로 사용자 요청으로 취급하지 않는다. 근거 없는 전제는 제거하게 하며 그 전제를 확인하는 새 질문을 제안하지 않는다. 질문 하나에는 한 문장으로 답을 요청할 수 있고, 길이를 채우기 위해 이미 답한 항목이나 새 요구를 추가하지 않는다. 이 보완은 검토의 거절 기준을 낮추거나 수정 횟수를 늘리지 않는다.

초안의 `sourceMessageIds`도 요청별 메시지 ID enum으로 제한한다. 원문 source 옆에 있는 질문 ID나 약속 ID를 출처로 잘못 넣는 출력을 생성 단계에서 제한하며, 최소 출처 하나와 기존 서버의 원문·숫자·담당자 표현 검증은 유지한다. 여러 상담의 스키마는 서로 공유해 수정하지 않는다.

초안에 보낼 원문 메시지는 ID·발화자·본문만 사용하고 `sentAt`은 전달하지 않는다. 약속도 원문 기한 `dueText`를 유지하되 계산된 `dueAt`과 확인 시각 `confirmedAt`을 제외한다. 분석과 화면의 날짜 계산은 그대로 유지한다. 직접 확인 기록이 있으면 `confirmedByUser=true`를 전달하고 없으면 해당 필드를 생략한다. 미기록을 ‘실제로 확인하지 않음’으로 해석하지 않으며, 원문에 없는 확인/미확인 사실을 모두 생성하지 않도록 명시한다. 생성과 검토·평가용 대조 검사는 같은 입력 함수를 사용한다.
