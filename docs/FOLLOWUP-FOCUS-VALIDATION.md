# 재문의 초안의 답변 중복·불필요한 부연 개선

기준: main `b8942ce` / 2026-11-16 / `gpt-5-mini-2025-08-07`. 결과 원문은 [평가 기록 폴더](../evals/results/followup-focus/)에 보관한다.

## 문제와 변경

고객은 실제 환불일을 물었는데 AI가 질문 제목을 `환불 예정일(언제 안내받을지/언제 환불되는지)`로 넓히면, 이미 안내 기한을 받았어도 초안에서 언제 알려줄지를 반복할 수 있었다. 복합 질문의 일부만 답변받은 경우에는 검토기가 원래 항목 전체를 다시 물어야 한다고 판단할 수도 있었다.

- 제목은 `topicHint`라는 식별 힌트로 전달하고, 요청 범위는 실제 고객 원문과 최신 대화로 판단한다. 저장된 제목은 변경하지 않는다.
- 답변받은 항목을 별도로 제공하며, 선택한 부분 답변에서도 받은 부분을 제외한다.
- 검토에 답변 중복 기준을 추가한다. 다섯 기준을 모두 통과해야 저장한다.
- 미정·확인 중인 정보는 답을 받은 것으로 취급하지 않는다. 실제 상충, 별도로 물은 날짜·상태, 실제 누락 서류는 유지한다.
- 불필요한 서두·괄호의 동의어·강조를 줄인다. 단순 문체 차이 때문에 API 검토를 추가하지 않는다.
- 구체적인 서류 답변을 임의로 불완전하다고 해석하여 추가 서류나 충분 여부를 묻지 않는다. 업체가 일부 목록이라고 명시하거나 실제 두 서류 중 하나가 빠진 경우는 구별한다.
- 환불일을 카드 입금 반영일로 바꾸거나 완료일을 완료 여부와 택일하는 질문으로 넓히지 않는다.
- 준비된 수리·환불 예제도 남은 금액만 묻도록 맞췄다.

기존 생성·검토 한 쌍, 오류 시 최대 한 번 재작성·재검토 구조를 유지한다. 추가 API 단계나 근거 문장의 기계적인 삭제는 없다. 기존 저장 초안·직접 편집 내용은 유지하며 새 작성부터 적용한다.

## 평가 설계

실제 API 생성 평가는 총 20건이다. 이전 실제 웹에서 관측한 환불 기록 1건, 부분 답변·미정·상충·영어·자료 누락 대조 12건, 기존 배송·환불·구독 평가에서 가져온 재문의 7건(S02/S04/R02/U02/NS01/NR02/NU03)이다. 이 평가는 질문 상태를 고정하고 실제 서비스의 생성·검토·수정 경로를 실행한다. 분석 48건을 새로 평가한 결과는 아니다.

별도로 정상 초안 13개와 의도적인 오류 초안 17개를 실제 서비스 검토기에 넣는다. 정상 문의를 잘못 거절하지 않고 중복·확대·누락을 구별하는지 확인한다. 생성기와 같은 모델의 검토 성적을 독립적인 정확도로 해석하지 않는다. 생성 결과는 정규식 보조 검사뿐 아니라 원문과 직접 대조한다.

기준 구현의 고정 사례 4건 재실행에서는 환불 제목 사례와 정정된 금액 사례는 정상 문장을 냈다. 반품비 사례에는 이미 받은 항목이 불필요한 제목으로 붙었고, 영어 자료·기간 사례는 서류를 다시 묻지 않은 정상 초안을 검토기가 거절해 저장에 실패했다. 이는 4건의 관측이며 전체 서비스 실패율로 일반화하지 않는다. 과거의 문제 출력이 매번 재현된다고도 주장하지 않는다.

## 수정 과정의 실패도 보존

| 실행 | 발견한 내용 | 대응 |
|---|---|---|
| v1 생성·검토 | 미정인 날짜·기간·안내 시점을 이미 답변된 것으로 잘못 처리. 처리 완료일 질문에 완료 여부를 대안으로 추가 | 실제 정보 충족과 단순 회신을 구분하고 요청 정보의 종류 보존 |
| v2 원문 대조 | 환불일을 카드 반영일로 확장, 안내된 거래 ID 외에 추가 서류를 임의 질문 | 두 확장을 제한하고 실제 누락 서류 대조 추가 |
| v2 보조 검사 | 정상 표현인 `안내 예정일`을 탐지하지 못해 오탐 | 동의어 검사 보완. 원본 결과는 보존 |
| v3 검토 | 임의의 추가 서류 질문 1개를 잘못 승인 | 프롬프트뿐 아니라 검토 스키마의 추가 요청 기준에도 구체적인 구별 명시 |
| v3 보조 검사 | 정상 초안의 `receipt ID에 더해 신분증 사진도 필요한지`라는 식별 맥락을 중복 질문으로 오탐 | 단순 단어 등장과 실제 재요청을 구별하고 정상 표현 단위 테스트 추가 |
| `generated-final` / `reviewer-final` | 생성 20건은 통과했으나 F03 정상 기간 질문 거절·임의 추가 서류 승인 발견 | 파일 이름과 관계없이 최종 통과 기록으로 취급하지 않음. 복합 질문의 누락 기준 수정 |
| 서류 집중 대조 | 지침 정리·별도 사실 요약 출력 실험에도 추가 서류 오류 승인이 남음 | 요약 출력 필드는 채택하지 않음. 받은 정보→남은 정보→초안 대조 순서는 유지하고, 영어의 목록 완전성 추측 금지 기준을 명시 |
| `generated-verified` / `reviewer-verified` | 기간 질문을 완료 날짜로 바꾼 생성 1건, 압축한 검토 지침에서 환불 단계·승인 여부·대체 상태 대조 회귀 | 소요 기간과 날짜를 구별. 기존 상세 검토 지침을 복원하고 범위 보완만 추가 |
| 복원 후 대조 | 30개 중 이미 정정된 금액을 다시 묻는 오류 1개 승인 | 명시적으로 정정되어 확정된 금액은 미해결 상충과 다르다는 검토 기준 보완 |
| 복원 후 보조 검사 | 정상 영어 `require` / `complete list in addition`을 각각 `required` / `full, additional` 표현만 찾는 검사에서 오탐 | 의미 기준을 바꾸지 않고 동의어만 보완. 실제 출력·실패 채점 보존 후 API 호출 없이 재채점 |

v3 생성 문장 20개를 직접 대조했을 때 위 보조 검사 오탐 외에 기준 위반은 발견하지 않았다. 다만 검토기의 오류 승인 1개가 있어 해당 상태로 종료하지 않았다. 실패 결과를 성공으로 덮어쓰지 않는다.

## 최종 검증

생성 20건은 [원본](../evals/results/followup-focus/generated-restored-review.json)과 [재채점](../evals/results/followup-focus/generated-rescored.json), [원문 대조](../evals/results/followup-focus/manual-restored-review.json)를 함께 본다. 최초 보조 채점은 18/20이며 위 영어 동의어 오탐 2건을 바로잡은 재채점과 원문 대조는 **20/20**이다. 원본 실패 결과를 수정하거나 같은 답을 얻을 때까지 API를 재호출한 것이 아니다.

이후 정정 금액 검토 기준을 보완한 최종 코드에서는 영향 사례 F07/F08/F09를 실제 생성·검토로 다시 실행해 **3/3** 통과했다([기록](../evals/results/followup-focus/generated-corrected-amount.json)). 상충이 남은 환불 수단은 물으며, 정정되어 받은 금액은 제외하고 날짜만 묻고, 같은 원문에 남은 금액·날짜 두 항목은 모두 보존했다. 최종 코드의 전체 검토 대조는 [별도 기록](../evals/results/followup-focus/reviewer-corrected-amount.json)으로 확인한다. 앞선 `final`·`verified` 이름의 파일은 중간 실패 기록이며 최종 통과를 뜻하지 않는다.

최종 검토 대조 **30/30**을 통과했다. 정상 초안 **13/13 허용**, 의도적인 중복·확대·누락 초안 **17/17 거절**이다. 이는 개발 중 재사용한 고정 회귀 자료의 결과이며 새로운 문의 전체에 대한 일반 정확도가 아니다. 마지막 보완 후 생성 영향 3건과 전체 검토 대조를 재평가했으며, 전체 생성 20건을 최종 코드에서 다시 실행했다고 주장하지 않는다.

### 실제 문장 변화

| 상황 | 보완 전 관측 또는 오류 대조 | 보완 후 실제 생성 |
|---|---|---|
| 반품비는 받았고 환불액만 모름 | `반품비와 최종 환불액: 최종 환불액을 확인하여 알려주시기 바랍니다.` | `최종 환불액을 알려주시기 바랍니다.` |
| 자료는 안내받았고 심사 기간만 모름 | 자료 질문까지 다시 넣어야 한다는 잘못된 검토로 저장 실패 | `Could you please let me know how long the review will take?` |
| 금액이 명시적으로 정정됐고 날짜만 미정 | `정정된 환불 금액과 실제 환불 날짜를 알려주세요.`는 거절할 오류 대조 | `실제 환불 날짜를 알려주시겠습니까?` |

### 실제 웹·회귀 검사

- 실제 OpenAI API + Chrome에서 환불 상담과 영어 계정 복구 이메일의 **등록→분석→새 답변 반영→재문의 생성→직접 편집→저장→복사→새로고침**을 통과했다. 질문 상태·근거·전후 비교·문의 진행 요약·모바일 가로 넘침을 검사했고 브라우저 오류는 없었다([최종 웹 기록](../evals/results/followup-focus/browser-final.json)).
- 환불 웹 결과: `반품한 이어폰의 환불 예정일을 알려주시기 바랍니다.` 금액·결제수단·이미 받은 안내 기한을 되묻지 않았다.
- 영어 웹 결과: `Please provide my case reference number for the account recovery.` 이미 받은 자료 안내·심사 기간·수신 확인을 되묻지 않았다.
- 단위 테스트 **257/257**, JavaScript **136개** 문법 검사, Chrome 회귀 **9종** 통과([로컬 기록](../evals/results/followup-focus/local-regression.json)). 취소·동시 수정·검토 실패 시 이전 초안 보호, 모든 질문이 답변된 경우 API 미호출도 포함한다.
- 보조 채점의 동의어 수정 후 관련 테스트 12개를 추가 실행해 통과했다. 생성 결과 자체는 바꾸지 않았다.

## 범위와 한계

이번 변경은 초안 생성·검토와 준비된 예제에 한정한다. 분석 함수, 일반·경계·완료·이메일·집중 분석 프롬프트와 분석 스키마는 기준 구현과 동일한지 별도 비교했다([비교 결과](../evals/results/followup-focus/analysis-unchanged.json)). 실제 웹의 등록·새 답변 분석 흐름도 별도로 검증한다.

고정된 합성 사례와 이전 기록에 대한 회귀 결과이며 모든 문의에서 오류가 없다는 보장은 아니다. 별도 인간 평가자의 검수가 아니다. 짧은 문장 생성이 속도·비용 절감률을 보장하지 않으며 이번 작업에서는 그런 수치를 주장하지 않는다. 입력 분석 자체가 잘못된 모든 경우를 초안 단계가 복구한다고 주장하지 않는다.
